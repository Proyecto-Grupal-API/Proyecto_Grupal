# 2.8 — Adaptador optativo de autorización del campus

CashAuthorizationProvider continúa como puerto financiero. El proveedor optativo CampusCashAuthorizationProvider acepta solo identidades user:OID derivadas por los controladores web y nunca service: ni OID sin prefijo. Comprueba cuenta existente/activa/verificada, principal del núcleo, permiso y asociación validada en cada llamada. Para acciones distintas de read/approval_read exige secreto2FAy confirmación. No usa roles embebidos y no cachea permisos positivos. Fallos de dependencia se reportan y devuelvenfalse, conforme al puerto booleano existente: las operaciones se bloquean con403; no confundir con que se haya demostrado ausencia definitiva de un rol. Una configuración de proveedor inválida bloquea con503 al resolverlo.

## Capacidad por acción

|Acción del contrato|Capacidad|
|---|---|
|read|financial.cash.read|
|operate|financial.cash.operate|
|adjust|financial.cash.adjust|
|close|financial.cash.close|
|manage|financial.cash.manage|
|recover|financial.cash.recover|
|approval_read|financial.cash.approval_read|
|approval_manage|financial.cash.approval_manage|
|approval_review|financial.cash.approval_review|

Todas se registran bajo módulo2/submódulo8. Los permisos generales previos module.2.8.* NO se transforman automáticamente en estas acciones. El formulario de asignación mixta muestra un bloque específico2.8. Una asignación completa nueva incluye el catálogo vigente; una asignación completa antigua sigue conservando solo su lista original. El administrador global tiene las capacidades del catálogo, pero necesita asociación válida; no inventar ID ni saltar validación del contexto.

operate habilita las acciones operativas existentes del mismo contrato (apertura, ingresos/salidas físicas, recargas/retiros autorizados). No habilita adjust/close/recover/manage/approval_review. Estas capacidades no sustituyen límite económico, disponibilidad de efectivo/wallet, operador del turno, confirmación del titular, motivo, idempotencia, ni segunda aprobación definida por políticas. No se modificaron esos servicios. Un supervisor también se revalida con este adaptador al ejecutar una solicitud previamente aprobada.

Los tokens de servicio de la API de Caja no obtienen permisos por convertir su subject en usuario. Con este proveedor siguen rechazados: su futura autorización necesita un contrato de identidad de servicio/delegación independiente. Las pruebas existentes de API usan sus dobles confiables habituales; esto no constituye habilitación productiva de clientes.

## Activación

En.envestablecer FINANCIAL_CASH_AUTHORIZATION_PROVIDER=campus y mantener CAMPUS_AUTHORIZATION_ENABLED=true. Ejecutar config:clear y reiniciar procesos de desarrollo. La instalación conserva pendingpor defecto. Cambiar a pendingdesconecta la autorización sin borrar roles ni operaciones. El proveedor está registrado en CashCampusIntegrationServiceProvider, después del proveedor de la app; el binding financiero previo queda disponible si se retira este proveedor. La dependencia nueva del núcleo está solo en el adaptador, no en los servicios de caja.
