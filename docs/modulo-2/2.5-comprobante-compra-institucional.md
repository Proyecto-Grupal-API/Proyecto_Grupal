# Comprobante de compra con BECA institucional

Base: `cb8e243`. Complementa la consulta existente de comprobantes de compras en pantalla, API autorizada y PDF. No agrega rutas, roles, permisos, migraciones ni movimientos financieros.

## Comportamiento

El total original y el estado de la compra se conservan. Para una compra institucional consistente, `purchase.institutional` contiene:

| Campo | Significado |
|---|---|
| `funding_type` | Literal `INSTITUTIONAL_BECA` |
| `observed_at` | Fecha de consulta del estado de devoluciones |
| `covered_amount_cents` | Importe original cubierto por la BECA |
| `refunded_amount_cents` | Suma de devoluciones institucionales completadas |
| `net_amount_cents` | Original menos devuelto; no representa saldo disponible ni liquidación al negocio |
| `restored_bonus_amount_cents` | Parte devuelta al bono mediante el flujo de BECA vigente |
| `released_budget_amount_cents` | Parte liberada al presupuesto mediante devolución de BECA cerrada |

Una solicitud de devolución pendiente, aprobada o rechazada no se cuenta como dinero devuelto. En una devolución completa, el neto puede ser cero y el total original sigue siendo el de la compra. Si la BECA estaba cerrada, se aclara que lo liberado al presupuesto no incrementó la wallet ni reactivó el bono.

Las compras heredadas o no institucionales reciben `purchase.institutional=null`; no se les atribuye financiamiento retroactivo. Los demás tipos de comprobante siguen con su estructura existente.

La pantalla reutiliza el formateador exacto de centavos institucional: acepta enteros seguros o cadenas canónicas y no divide importes mediante punto flotante. Los valores monetarios inválidos no se presentan como cero.

## Lectura e integridad

La búsqueda original exige pertenencia a la wallet antes de consultar evidencia interna. El nuevo lector detecta obligación, marca del bono o compromiso; si hay evidencia institucional incompleta no la presenta como un bono ordinario.

La proyección usa transacción y el mismo orden de bloqueo presupuesto → bono que los escritores. Los bloqueos `UPDLOCK` serializan esta lectura con las escrituras para evitar una conversión S→X cuando una liquidación modifica primero su obligación. No se actualizan filas ni se crean eventos, folios, auditorías financieras o saldos. Se reutilizan las verificaciones de integridad presupuestaria y del bono, y se comprueba la suma por destino de devolución.

Solo salen importes de la propia compra y la fecha de consulta. No se exponen identificadores internos de presupuesto/obligación, otorgantes, pagadores, referencias bancarias ni importes liquidados al negocio. El documento muestra cobertura BECA; no certifica respaldo bancario o pago institucional al comercio.

## Verificación

`InstitutionalReceiptTest` cubre lectura sin cambios, pantalla del propietario, privacidad, devoluciones pendientes/aprobadas/rechazadas/completadas, devolución de BECA cerrada, devolución total, recursos ajenos, evidencia alterada, PDF real y compatibilidad con compras heredadas.

El paquete incluye verificador de testing y compilación Vue. Pest usa 512 MB exclusivamente durante esa ejecución, sin editar `php.ini` ni `.env`. No ejecuta migraciones ni llamadas reales a E1/E4. Los usuarios y autorizadores sintéticos se limitan a testing; las transacciones SQL de las pruebas se revierten.

La preparación se revisó estáticamente. Las pruebas PHP/SQL y la revisión visual de un PDF descargado deben ejecutarse en el entorno del responsable antes de declarar validada esta entrega. No es necesario repetir la suite completa de 897 casos salvo que estos cambios o sus resultados revelen otro problema; el verificador ejecuta las regresiones de comprobantes y de consumo/devolución institucional pertinentes.
