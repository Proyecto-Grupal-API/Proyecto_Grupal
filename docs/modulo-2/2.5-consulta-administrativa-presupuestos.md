# Consulta administrativa institucional

Base: ae697c3. La pantalla GET /finanzas/presupuestos-institucionales presenta presupuestos BECA, resumen por negocio, compras/obligaciones y liquidaciones externas. Reutiliza InstitutionalObligationQueryService; no agrega emisores, ejecutores de pago ni autorizadores permisivos.

## Acceso

InstitutionalBudgetAuthorization conserva su binding Pending: deniega todo. budget.read.all permite enumerar; budget.read permite consultar únicamente un UUID autorizado. Son acciones internas del contrato E2, no roles institucionales nuevos ni permisos aprobados de E1. La concesión de lectura nunca debe conceder budget.approve, budget.commit, purchase.pay o settlement.record.

La identidad sale de la sesión nativa. Se vuelve a consultar el usuario en MongoDB, su elegibilidad, correo verificado, segundo factor configurado/confirmado y registro cd_session_id propio no revocado. La guarda precede al seguimiento de dispositivos para evitar reparar una sesión faltante. No prueba una autenticación de segundo factor reciente. Se valida autoridad en cada solicitud, antes de consultar SQL financiero. Fallos de dependencia devuelven 503 sanitizado y no conceden acceso.

Finanzas muestra el enlace solo cuando canList confirma lectura global. Con el binding actual, el enlace permanece oculto y la ruta devuelve 403 a una sesión válida sin autoridad. El lector contextual utiliza el enlace directo con ?budget=UUID autorizado. No se añade ningún botón para conceder autoridad. No usar Tinker ni alterar Pending para habilitarlo.

## Datos y límites

Filtros: budget UUID, business identificador canónico, view businesses/obligations/settlements, page 1–1000000 y per_page 1–20. No acepta selectores actor_id/subject_id. Los detalles y el filtro de negocio exigen un presupuesto. Se vuelve a autorizar el UUID recibido. La paginación global lista presupuestos; la de detalle lista negocios, compras o liquidaciones.

Totales y hallazgos corresponden a todos los negocios de cada presupuesto seleccionado, aun al filtrar las filas por negocio. Se muestran estado almacenado, importes, observación y diferencias. ACTIVE no certifica vigencia, autoridad ni efectivo disponible. Pagos registrados no liberan consumido. Una pantalla consistente no certifica respaldo bancario.

Importes se reciben como cadenas de centavos y se presentan con BigInt, preservando agregados mayores al rango entero PHP/JavaScript. Un dato ausente o inválido aparece como “Importe no disponible”, nunca como cero. Vue escapa las referencias; no se usa v-html. Se muestran propósito y referencia institucional de presupuestos ya autorizados; no pagador, destinatario financiero ni identidad del beneficiario en el reporte. Las props compartidas habituales de Inertia mantienen el usuario autenticado. Cache-Control no-store, private.

Solo GET/HEAD. La lectura puede actualizar metadatos normales de sesión/dispositivo o consumir el contador de solicitudes; no cambia importes, evidencias financieras, presupuestos, bonos, compras ni liquidaciones.

## Preparación del esquema de desarrollo

No hay migraciones nuevas. Migrate-Development.ps1 aplica individualmente las cuatro migraciones institucionales existentes 220000/230000/240000/250000, sin fresh, rollback ni semillas. Antes requiere APP_ENV=local, SQL Server local, nombre configurado y nombre real campus_digital_financial, y tablas financieras base. Si la comprobación falla no migra. Una interrupción posterior puede dejar migraciones anteriores aplicadas; conservar salida y corregir, sin borrar evidencia. No modifica .env ni MongoDB desarrollo.

Verify -PrepareDevelopment ejecuta primero pruebas aisladas y build; restaura variables de proceso y después prepara desarrollo. No usar esta opción en un servidor compartido/productivo. Los nombres distintos se rechazan deliberadamente. La preparación no crea registros que permitan usar funciones bloqueadas.

## Validación

14 casos web nuevos: denegación, alcance global/contextual, revisión de autoridad/sesión/cuenta, filtros antes de SQL, fallos sanitizados, ausencia de endpoint de escritura y visibilidad del enlace. Los autorizadores positivos son dobles exclusivos de tests con bases exactas de testing. Cuatro casos Node verifican presentación monetaria exacta.

Se verificaron aquí compilación de ambos SFC Vue y cuatro pruebas Node. PHP/Pest, SQL Server y build completo requieren ejecución en Windows. Verify prepara únicamente el esquema de testing antes de las pruebas; esa base MongoDB es reiniciada por TestCase. No ejecutar contra datos que se necesiten conservar. -FullFinancialSuite amplía la regresión financiera.
