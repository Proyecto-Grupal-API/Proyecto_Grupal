# 2.5 — Consumidor del contrato financiero de Identidad

## Base y alcance

Base exacta: Modulo 2 bad1bf3ec87ddba036aa4c2cebae15426b7740c0, con regresion previa reportada por el usuario de 567 pruebas y 4546 aserciones. Esta entrega prepara exclusivamente el consumidor de la especificacion E1 recibida el 26/10/2026. No integra otros modulos ni restaura la propuesta de roles rechazada.

El ZIP de E1 recibido corresponde a 86111548a7659ffa3dab4fd6ee441bb70160b3d9. No contiene el endpoint financiero descrito ni la nueva politica. El merge f609bd3b23284b0f4f043fc63c577adf2e89f0e1 tampoco incluye Modulo 2 ni esa ruta. Las 36 pruebas/75 aserciones de E1 son resultados informados por ese equipo sobre su desarrollo interno, no pruebas ejecutadas por esta entrega ni certificacion HTTP conjunta.

Instalar el consumidor no publica el endpoint de E1. Se entrega apagado, sin credenciales. No se cambia .env, no se crean roles, permisos, usuarios, contextos, bonos ni asignaciones.

## Componentes

- IdentityFinancialAuthorizationClient: OAuth client_credentials y consulta tecnica de capacidad.
- IdentityBonusAuthorizationProvider: adapta los contratos existentes BonusAuthorizationProvider / ContextualBonusAuthorizationProvider; no importa clases de E1.
- FinancialIdentityAuthorizationServiceProvider: registra SOLO el binding de bonos; apagado conserva PendingBonusAuthorizationProvider.
- IdentityFinancialAuthorizationUnavailable: error propio con reporte sanitizado y render HTTP 503.
- financial:bonus-authorization-check: consulta diagnostica explicita, sin emision ni movimientos.

No se modifica BonusService, BonusAdministrationService, FinancialWebAuthorizer, controladores, rutas, modelos de roles, esquemas SQL/Mongo ni Vue. El unico archivo existente modificado es bootstrap/providers.php para cargar el provider nuevo DESPUES del AppServiceProvider.

## Contrato HTTP consumido

POST {ORIGIN}/api/oauth/token (form): grant_type=client_credentials, client_id, client_secret, scope=identity:financial-authorization:check.

Se exige respuesta HTTP 200 JSON con access_token no vacio, token_type Bearer, expires_in entero positivo y scope que incluya el requerido. No se usan credenciales de usuarios ni un token de compras de nuestro servidor. El cliente de servicio debe registrarlo E1 en su servidor cuando publique la entrega.

POST {ORIGIN}/api/v1/identity/financial-authorization/check (JSON):

```json
{
  "subject_id": "507f1f77bcf86cd799439011",
  "bonus_type": "BENEFICIO",
  "operation": "issue",
  "scope_type": null,
  "scope_id": null
}
```

Los IDs del ejemplo son sinteticos. Los tipos son BECA, CAMPANIA, BENEFICIO, CATEGORIA y NEGOCIO exactamente como nuestros enums. subject_id debe ser el identificador canonico de E1, 24 hex; el adaptador normaliza a minusculas. Un issuer_id de texto libre, con prefijo user:, o un SYSTEM no se transforma en una persona ni se mapea por correo. SYSTEM necesita un contrato separado antes de usarse con este proveedor.

| Tipo | Contexto enviado |
|---|---|
| Los cinco tipos, global | null/null explicitos |
| NEGOCIO contextual | business + identificador canonico del negocio |
| BECA o CAMPANIA contextual | Rechazado localmente, sin HTTP |
| BENEFICIO o CATEGORIA contextual | Rechazado localmente, sin HTTP |
| association, service, council | Rechazado en este contrato, sin ampliar el DTO legado |

BECA contextual con academic_program sigue pendiente: no se agrega ese contexto al DTO ni se interpreta programa academico como programa de becas. NEGOCIO contextual tiene formato admitido, pero E1 informo que su validador comercial aun no esta conectado. No habilitar su uso operativo hasta validacion conjunta. No se implementa un validador ficticio ni se consulta Mongo de otro dominio.

E1 realiza su composicion autoridad global O contextual exacta despues de validar el negocio. E2 envia UNA consulta por evaluacion y no realiza fallback a null/null si la contextual se deniega o falla. Un bono global no equivale a administracion global del campus ni otorga los otros tipos.

## Respuestas y seguridad

Solo HTTP 200 + JSON de objeto + authorized booleano es decision valida. true autoriza la capacidad tecnica; false la deniega. No se aceptan 1, "true", "false", null, listas, HTML, JSON roto ni otros codigos 2xx. Se exige Content-Type application/json (charset permitido) y se limita la envoltura a 8 KiB; OAuth admite hasta 32 KiB.

401/403 de E1 rechazan al SERVICIO o su concesion; no deben confundirse con authorized=false del sujeto. 422 indica incompatibilidad/solicitud invalida, 429 saturacion y 500/503 indisponibilidad. Todos se representan como IdentityFinancialAuthorizationUnavailable para el consumidor financiero; no concede permiso y el render HTTP propio devuelve 503 sin cuerpo externo. Se conserva el codigo de dependencia/HTTP solo para diagnostico interno. No se inventa un reason_code de E1.

La excepcion reporta codigo interno y estado HTTP, sin token, secreto, subject, cuerpo externo ni previous RequestException. Errores inesperados de programacion no se capturan genericamente dentro del cliente para presentarlos como una decision. El comando reporta los fallos inesperados mediante report(). No habilitar logging externo de cuerpos/headers OAuth.

No se siguen redirecciones, no se desactiva TLS, no hay retries automaticos, no hay cache positiva de decisiones ni cache persistente de tokens. Cada evaluacion valida nuevamente mediante un token nuevo. Timeout de conexion 3s y total 10s POR llamada: OAuth y check son dos llamadas separadas. El resultado es valido para la evaluacion realizada; no bloquea revocaciones posteriores ni ofrece atomicidad distribuida entre E1 y una transaccion SQL.

Origen configurado = esquema + host + puerto opcional, sin /api, ruta, query, fragmento ni credenciales. HTTPS en produccion. HTTP solo para loopback (localhost, 127.0.0.1, ::1) en APP_ENV local/testing. En despliegues entre contenedores/maquinas se necesita un origen HTTPS alcanzable; no rebajar la validacion para usar una direccion de muestra.

## Diagnostico

Con integracion apagada, el siguiente comando no hace HTTP y devuelve UNAVAILABLE / INTEGRATION_DISABLED, codigo de salida 2. Es comportamiento esperado, no una prueba aprobada del servidor E1:

```powershell
php artisan financial:bonus-authorization-check "507f1f77bcf86cd799439011" BENEFICIO
```

Con la integracion realmente disponible, sustituir por el ID canonico real. Para global, omitir ambos flags. Contextual NEGOCIO, solo despues de validacion comercial operativa en E1:

```powershell
php artisan financial:bonus-authorization-check "ID_CANONICO_REAL" NEGOCIO --scope-type=business --scope-id="NEGOCIO_CANONICO_REAL"
```

ID_CANONICO_REAL es un marcador, no ejecutar literalmente. No enviar secretos como argumentos.

Salida EVALUATED incluye authorized true/false, el contexto y human_consent_proven=false / bonus_issued=false. EVALUATED false termina con codigo 0, porque la consulta fue valida. Indisponibilidad termina en 2, entrada invalida/error inesperado en 1. El comando no invoca BonusService ni SQL, no asigna roles ni sustituye la prueba de sesion del actor.

## Lo que queda bloqueado y por que

FinancialWebAuthorizer sigue pendiente. Por tanto, NI habilitar este consumidor NI recibir un true por diagnostico abre automaticamente la pantalla de emision. Esto evita interpretar una capacidad tecnica como permiso para consultar todas las emisiones, cancelar bonos o gestionar caja.

El siguiente cambio de apertura web, cuando exista una entrega E1 verificada y asignaciones aprobadas, debera:
1. Derivar el emisor desde sesion web autenticada/registrada/vigente, elegibilidad y controles de seguridad acordados; nunca usar subject_id/issuer_id del navegador como prueba del actor.
2. Autorizar especificamente el tipo de emision, sin conceder bonus.view, view.all, cancel, cancel.all ni autoridad de caja por extension.
3. Alinear la guardia generica actual con la comprobacion tipada y su punto de revalidacion, preservando idempotencia y auditoria. No sustituir simplemente FinancialWebAuthorizer por un proveedor que permita todo.
4. Revisar las reglas financieras existentes de financiamiento, limites, restricciones y autoemision antes de abrir el flujo. Esta entrega NO certifica ni agrega esas reglas. BonusService conserva su comportamiento actual, incluido el tratamiento legado de denegacion por bool como InvalidArgumentException; no se afirma que todos los consumidores existentes ya respondan 403 tipado.
5. Mantener operaciones no definidas en el contrato deshabilitadas y acordarlas por separado. issue no autoriza cancel/addRestriction autonomos ni operacion SYSTEM.

No se pretende que un check aislado con client_credentials pruebe consentimiento humano. La identidad del sujeto y la autoridad institucional aprobada no son lo mismo. No se almacenan ni se convierten los roles tecnicos publicados por E1 en nuestras siete plazas descartadas.

## Pruebas y limites de esta entrega

Unitarias independientes sin bootstrap de Laravel: tipos/campos exactos, null/null, contexto, strict bool, estados HTTP, ausencia del validador, revocacion sin cache, errores OAuth/red, origen seguro, JSON invalido y reporte sin secretos. Usan PHPUnit + HTTP fake, sin SQL/Mongo ni credenciales reales.

Feature: resolucion del contenedor, flag apagado, adaptador real por flag, aislamiento del autorizador web, diagnostico sin filas/saldos, persistencia del contexto con respuesta positiva simulada SOLO en pruebas, denegacion/indisponibilidad sin escrituras y render sanitizado 503. Los HTTP fake son dobles de pruebas automatizadas, no proveedores simulados instalados para usuarios.

No hay PHP, PowerShell, Mongo ni SQL Server disponibles donde se preparo el ZIP. No se ejecutaron pruebas ni se afirma que pasaron. Verify debe correr en Windows con las bases de pruebas aisladas. Su preflight comprueba los nombres antes de arrancar TestCase, que elimina Mongo de pruebas. No existe certificacion conjunta HTTP E1-E2 en esta entrega.
