# 2.8 — Administración de cajas con historial, versiones e idempotencia

Base: e2d3820. La interfaz de caja anterior está verificada: 320 pruebas financieras / 2418 aserciones. Este bloque agrega alta y edición de cajas, historial administrativo y su interfaz. Conserva servicios de liquidación, turnos, ledger y saldos. Requiere una migración nueva en desarrollo y pruebas; no modifica .env.

## Modelo y auditoría

cash_registers agrega version con valor inicial 1 para filas existentes. cash_register_changes registra UUID, caja interna, versión, acción CREATE/UPDATE, estado anterior y posterior JSON, responsable, motivo, fecha, clave idempotente y hash de solicitud. La clave es única y existe una sola entrada administrativa por versión de caja.

No se inventa el historial anterior a esta migración. Las cajas existentes conservan su estado y versión 1; su primera edición auditada produce versión 2 con snapshot anterior. Las nuevas altas realizadas desde la administración generan versión 1 con before null. CashShiftService::createRegister se conserva como método interno compatible con fixtures y código previo; los endpoints administrativos pasan por el nuevo servicio auditado.

CashRegisterAdministrationService crea o edita la caja y guarda su historial dentro de la misma transacción SQL. Si falla la auditoría se revierten caja y versión. Reintentar la misma solicitud devuelve su snapshot original aunque posteriormente haya nuevas versiones: no sobrescribe cambios más recientes. Una clave reutilizada con diferente asociación, caja, actor, motivo o payload genera conflicto.

Actualización: name, status ACTIVE/INACTIVE, expected_version y reason. La versión consultada debe coincidir con la vigente; otra edición produce 409 y debe releerse. No se guardan modificaciones sin cambios reales. Asociación y moneda son inmutables en edición. Alta: name, currency y reason; asociación proviene de la ruta, estado inicial ACTIVE.

La actualización bloquea primero la caja, igual que la apertura/liquidación/cierre de turnos. Si existe un turno OPEN se impide desactivar. No elimina ni mueve cajas, turnos o registros contables. Tras cerrar el turno se puede desactivar; abrir una caja INACTIVE está bloqueado por el servicio existente. La reactivación se audita como otra versión. El diseño de bloqueo coordina operaciones concurrentes; las pruebas funcionales no pretenden ser una carga concurrente real.

## Permisos y rutas

Nuevo permiso del proveedor CashAuthorizationProvider: manage. Nuevo scope OAuth: financial:cash:manage. Ambos se requieren en escrituras API; financial:cash:operate no administra cajas. Historial requiere read y financial:cash:read para API. La autorización sigue siendo por asociación y actor confiable. PendingCashAuthorizationProvider permanece denegando.

| Método | Ruta relativa al prefijo de asociación | Permiso |
|---|---|---|
| POST | /registers | manage |
| PATCH | /registers/{registerId} | manage |
| GET | /registers/{registerId}/history | read |

API: /api/v1/financial/cash/associations/{associationId}.
Web: /finanzas/caja/asociaciones/{associationId}.
Página: /finanzas/caja/administracion, enlazada desde Caja y turnos.

Escrituras requieren Idempotency-Key. Alta/modificación/reintento exitosos devuelven 200. Errores de validación: 422; permisos: 403; UUID ajeno a asociación autorizada: 404; versión vieja, turno abierto o clave incompatible: 409. Colisión concurrente de restricción única usa el manejo 409 existente y permite reintentar con la misma clave.

API toma service:<sub OAuth>; web toma user:<ID de sesión>. actor_id del payload no se utiliza. El contexto web agrega booleano manage; no concede permisos ni expone datos administrativos. Todos los endpoints vuelven a autorizar en servidor. La pantalla puede ser visible con acciones deshabilitadas mientras se integra el adaptador real.

## Interfaz

Consultar asociación, listado paginado de cajas y versión, crear caja activa, editar nombre/estado y consultar historial paginado con antes/después, responsable, motivo y fecha. La moneda se puede elegir al crear y queda de solo lectura al editar. El estado se cambia desde edición; la restricción de turno abierto se comprueba en SQL, incluso si el navegador tenía datos antiguos.

El formulario conserva URL, payload y clave para reintentar tras conflicto o respuesta desconocida. Los campos y selección se bloquean mientras exista solicitud pendiente. El descarte explícito no cancela una operación y advierte revisar listado/historial. Las claves se conservan durante la vida de la página; si se recarga o se cierra antes de confirmar, revisar historial antes de iniciar una solicitud nueva. No se afirma persistencia de solicitudes entre recargas del navegador.

Consultar/administrar no son el mismo permiso: una cuenta puede consultar historial sin modificar; un administrador con manage puede crear aunque no tenga read, pero necesita read para listar y seleccionar cajas existentes desde la pantalla. La administración no usa saldos de wallet.

## Migración y verificación

Nueva migración: 2026_10_09_190000_add_cash_register_administration.php. No se modifican migraciones aplicadas. Apply-Changes.ps1 verifica todos los hashes antes de escribir, ejecuta php -l y hace respaldo. Verify-Changes.ps1 -MigrateDevelopment aplica la migración nueva a desarrollo y campus_digital_financial_testing. Restaura variables de entorno de proceso y mantiene conciliación de caja desactivada durante suite anterior, activándola solo para diagnóstico final.

Nueve pruebas nuevas: alta/reintento/snapshot original tras edición; clave reutilizada con otra solicitud; versión vieja/reintento de edición tras cambios posteriores; desactivar con turno abierto/cierre/reintento/reactivación; rollback al fallar historial en alta y edición; scopes y asociación independientes; API actor/estado/historial/UUID ajeno/campos inmutables; web sesión/pending/roles históricos; web auditoría y separación read/manage.

El verificador ejecuta administración, caja web, API y seguridad de roles; luego suite financiera completa, conciliación diagnóstica, rutas y npm run build. La prueba web previa se ajusta para esperar el nuevo permiso manage=false.

Revisión local: scripts/templates de Cash y CashRegisters compilados con Vue; imports App, rutas, modelo/casts/migración, manifiesto y ZIP contrastados; servicios anteriores sin cambios. No hay PHP, SQL Server ni MongoDB en este entorno. La sintaxis y pruebas completas deben verificarse en el equipo del proyecto antes de guardar el commit.
