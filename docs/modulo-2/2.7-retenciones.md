Base: bloque backend 2.10 que pasó 247 pruebas / 1525 assertions en el equipo del usuario. Este paquete es incremental; conserva las devoluciones existentes.

## Aplicación

Extrae el ZIP en `C:\Proyectos\Campus-Digital-2.7-retenciones`. Desde `C:\Proyectos\Campus-Digital`:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\Proyectos\Campus-Digital-2.7-retenciones\Apply-Changes.ps1" -ProjectPath "C:\Proyectos\Campus-Digital"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\Proyectos\Campus-Digital-2.7-retenciones\Verify-Changes.ps1" -ProjectPath "C:\Proyectos\Campus-Digital" -MigrateDevelopment
```

Ejecuta los comandos separados, empezando por Apply. El instalador revisa hashes del corte base, hace lint de los PHP antes de copiar y crea respaldo. Verify aplica la migración en desarrollo/testing, ejecuta las 17 pruebas nuevas y después toda la suite financiera. Usa `-TestDatabase nombre` si cambiaste el nombre de la base de testing. No copies manualmente carpetas completas sobre el proyecto.

## Alcance de este bloque

- WalletHoldService: crear, liberar, capturar el importe completo y liberar vencidas.
- Estados ACTIVA, LIBERADA, CAPTURADA, EXPIRADA; referencias, motivo, actor y fechas.
- Duración máxima por operación, sin límites de negocio inventados.
- Ledger central con deltas disponibles/retenidos y transacciones idempotentes.
- Captura desde retenido sin volver a debitar disponible; rollback si el cierre falla.
- Conciliación del disponible y retenido compatible con movimientos históricos.
- API y comando de vencimiento, permisos independientes y actor OAuth confiable.

## Política de vigencia

Actualización posterior al bloque de reversos (8a576ca): las duraciones ahora se administran en `wallet_hold_policies` mediante la API `/hold-policies`. Ver [políticas administrables](2.7-politicas-retencion.md). El antiguo mapa `FINANCIAL_HOLD_MAX_SECONDS` ya no autoriza retenciones nuevas.

Cada retención conserva el identificador, versión y duración máxima de su política al crearse. Las retenciones históricas sin estos campos conservan su vencimiento; las modificaciones solo afectan a solicitudes nuevas. Las pruebas crean TEST_CHECKOUT como fixture en la base de testing, sin fijar plazos de producción. No se modificó `.env`.

Vencimiento manual:

```powershell
php artisan financial:expire-holds
```

Programación opcional: `FINANCIAL_HOLD_SCHEDULE_EXPIRATION=true`. Se ejecuta cada minuto cuando la infraestructura ejecuta `schedule:run`, con locks del scheduler. Hasta habilitarlo, el comando manual está disponible. Una retención vencida no se puede capturar aunque aún no haya pasado el proceso de liberación. Su dinero permanece retenido hasta liberar; nunca se considera gastado por vencer.

## Contrato API

| Método | Ruta bajo /api/v1/financial | Scope |
|---|---|---|
| POST | /holds | financial:write |
| GET | /holds/{holdId} | financial:read |
| POST | /holds/{holdId}/release | financial:hold:release |
| POST | /holds/{holdId}/capture | financial:hold:capture |

POST requiere Idempotency-Key. Crear recibe wallet_id, amount_cents, operation_type, expires_at, reason, reference_type y reference_id. Cerrar recibe reason. El actor se deriva de oauth_client_id; no se toma del body. Repetir con la misma clave y datos devuelve la operación existente; reutilizarla para otra solicitud/cierre produce 409. Falta de datos/cabecera: 422; falta de token: 401; scope incorrecto: 403; inexistente: 404; regla de negocio incumplida: 409.

Los scopes autentican servicios autorizados, no al usuario humano. Un consumidor debe vincular su sesión humana y no permitir que un navegador elija libremente wallet/operación destino. No se concedieron grants a clientes ni se crearon permisos globales en identidad.

La captura consume valor retenido y devuelve su transacción. No acredita por sí sola una wallet comercial ni equivale a un pago mixto de PurchasePaymentService; esa orquestación requiere integración explícita. Los movimientos WALLET_HOLD_* se rechazan en los caminos legacy de devolución/reverso para evitar saltarse el ciclo de la retención.

## Contabilidad

| Transición por importe A | Disponible | Retenido | amount_cents (cambio del total) |
|---|---:|---:|---:|
| Retener | -A | +A | 0 |
| Liberar/vencer | +A | -A | 0 |
| Capturar | 0 | -A | -A |

La migración añade available_delta_cents nullable y held_delta_cents con default 0. Para historial anterior, disponible deriva de COALESCE(available_delta_cents, amount_cents). La API de ledger devuelve ambos deltas, para no interpretar una retención monetariamente neutra como una ausencia de movimiento. balance_after_cents conserva su significado histórico de saldo disponible.

## Verificación y límites

Aquí no están disponibles PHP ni las bases del usuario; los nuevos tests y php -l NO se ejecutaron en este entorno. Se revisaron imports, diferencias del paquete, manifiesto y preservación de rutas. El instalador realiza lint antes de modificar el proyecto y Verify ejecuta las pruebas reales. La concurrencia se controla con locks wallet -> hold y unicidad de claves; las pruebas nuevas validan idempotencia y rollback, no una simulación de carga con múltiples procesos.

No ejecutes rollback después de registrar retenciones reales sin un plan para conservar su historial y sus saldos: down elimina tabla/columnas de esta funcionalidad.
