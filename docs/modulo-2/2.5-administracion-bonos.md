# 2.5 — Emisión y cancelación administrativa de bonos

Base: `35945ef`. Este bloque agrega una interfaz administrativa conectada a BonusService mediante una frontera transaccional y auditada.

## Acciones y permisos

FinancialWebAuthorizer mantiene su interfaz existente. Las acciones nuevas se resuelven a partir del usuario autenticado, nunca de roles autoasignados ni del cuerpo de la solicitud:

| Acción | Alcance |
| --- | --- |
| bonus.view | Consultar bonos emitidos por el propio usuario e historial administrativo |
| bonus.issue | Solicitar emisión; además requiere autorización de BonusAuthorizationProvider para USER, usuario y tipo |
| bonus.cancel | Cancelar saldo restante de bonos emitidos por el propio usuario |
| bonus.view.all | Extiende la consulta a otros emisores; exige además bonus.view |
| bonus.cancel.all | Extiende la cancelación a otros emisores; exige además bonus.cancel |

La pantalla puede abrirse como una vista sin datos administrativos cuando no hay permisos. Los endpoints de datos y acciones comprueban la autorización en el servidor. Las acciones y consultas de bonos ajenos fuera del ámbito autorizado devuelven 404. Ver todos no concede cancelar todos.

Se registra PendingBonusAuthorizationProvider como implementación predeterminada de la interfaz existente: deniega toda emisión mientras se conecta el proveedor confiable del Módulo 1. FinancialWebAuthorizer conserva su adaptador pendiente que deniega por defecto. Las pruebas inyectan implementaciones de prueba; no se habilitan privilegios en desarrollo ni se agregan botones para autoasignar roles. Sustituir posteriormente ambos adaptadores no requiere cambiar ni desconectar la interfaz.

## Emisión

El beneficiario es una cuenta User existente en MongoDB, identificada por su ObjectId de 24 caracteres hexadecimales y sin activación pendiente. Se emite como beneficiary_type USER y issuer_type USER; el issuer_id se deriva de la sesión. No se admiten emisores o actores suministrados por el cliente. La comprobación de cuenta devuelve únicamente identificador y nombre a operadores con bonus.issue; no expone correo, credenciales o perfil completo.

La interfaz registra MXN, importe en pesos convertido a centavos enteros, tipo, fechas, combinabilidad, uso parcial, referencia externa opcional, motivo y restricciones iniciales. Las fechas de captura usan la zona del dispositivo, visible en el formulario; se envían con zona explícita y se normalizan al almacenamiento de la aplicación. La vigencia debe terminar después de su inicio y en el futuro para una nueva emisión. Las fechas equivalentes en distintas zonas producen el mismo contenido canónico para reintentos.

Negocio y Categoría requieren una restricción inicial del mismo tipo. No se admiten restricciones duplicadas o destinos vacíos. Los identificadores de destino no se validan contra catálogos de otros equipos: esa integración requiere su contrato. Las restricciones, bono y movimiento inicial se guardan juntos; si fallan, se revierte todo. No existe en este bloque edición posterior de restricciones sobre un bono ya emitido.

El importe máximo de la validación HTTP corresponde al entero seguro de JavaScript, no a una política económica. Los límites empresariales de emisión y beneficiarios autorizados deben resolverse en los proveedores confiables cuando se acuerde el contrato.

## Idempotencia y auditoría

Todas las mutaciones requieren Idempotency-Key (ASCII: letras, números, punto, guion, guion bajo y dos puntos; máximo 255). La llave se normaliza a minúsculas para ser consistente con la colación habitual de SQL Server. Se usa un mutex SQL por llave, índice único y hash de actor, acción y contenido normalizado. Solicitudes concurrentes sobre la misma llave devuelven 409 mientras una está en curso. Llave repetida con solicitud distinta o administrador distinto devuelve 409; repetición exacta autorizada devuelve 200 y el comprobante original. La primera operación crea el comprobante con 201.

BonusAdministrativeOperation conserva UUID, bono, actor user:ID, acción, motivo, hash, contenido, fecha y snapshots anterior/posterior con saldo y condiciones. Se inserta en la misma transacción SQL que el bono, restricciones y ledger. No hay endpoints para editar o borrar esos registros. La llave y hash no se exponen en el historial web.

Las respuestas de reintento contienen la fotografía de la operación original, no una afirmación del saldo actual. Los permisos actuales se vuelven a comprobar antes de devolver una operación ya registrada. La comprobación de vigencia/beneficiario para una nueva emisión se realiza después de buscar la operación original: repetir una emisión exitosa más tarde no la vuelve a emitir ni reinterpreta su vigencia.

El formulario congela el contenido y conserva su llave después del primer envío. Reintentar utiliza los datos originales; Nueva solicitud es una emisión nueva intencional. Ante una respuesta de red incierta, reintentar antes de iniciar una solicitud nueva.

## Cancelación

La cancelación exige motivo, permiso y ámbito de emisor. Usa el bloqueo del bono y las reglas de BonusService. Solo cancela el saldo restante; no revierte consumos anteriores ni acredita la wallet. Se registra un solo movimiento CANCELACION y un snapshot antes/después. Un reintento exacto devuelve el comprobante; una llave nueva sobre un bono ya cancelado se rechaza.

Agotados y vencidos no admiten cancelación. El servicio existente puede detectar vencimiento antes de rechazar; la nueva frontera transaccional revierte ese cambio si la cancelación falla, evitando movimientos parciales de una solicitud administrativa fallida. No cambia el comportamiento de otras llamadas existentes a BonusService.

## Rutas web

Prefijo `/finanzas/bonos/administracion`:
- GET `/`: pantalla administrativa.
- GET `/records`: listado paginado y filtro opcional por beneficiario.
- GET `/beneficiaries/{userId}`: comprobación de cuenta para emisión.
- POST `/issue`: emisión.
- POST `/{bonusId}/cancel`: cancelación.
- GET `/{bonusId}/history`: auditoría paginada.

Se conserva el middleware web de autenticación, correo verificado, sesión activa, seguimiento de dispositivo y protección CSRF de la aplicación. Las mutaciones se consumen desde Vue por endpoints de sesión; no se convierten en endpoints OAuth ni se modifica la API de servicios existente.
