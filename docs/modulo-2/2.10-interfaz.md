# 2.10 — Interfaz de límites, alertas y conciliación

Base: 8651a93, con interfaz 2.7 y corrección de fixtures verificadas. No modifica servicios financieros, API OAuth, esquema, .env, roles heredados ni el adaptador pendiente de autorización.

## Acceso

Finanzas → Límites, alertas y conciliación. Ruta /finanzas/controles. Tres secciones, filtros, paginación de veinte registros, estados vacíos y errores. Usa sesión autenticada, verificación, sesiones/dispositivos y protección CSRF existentes.

La página no incluye registros administrativos en sus props. Solo consulta los endpoints de cada sección cuando la capacidad correspondiente está habilitada. PendingFinancialWebAuthorizer permanece registrado: con el contrato de roles pendiente las consultas y acciones administrativas se deniegan en servidor con 403. La pantalla permite ver el estado de permisos; no presenta datos ficticios.

## Autorización humana

Se reutiliza FinancialWebAuthorizer del 2.7. Acciones globales:

- limits.view: lista e historial.
- limits.manage: alta/edición/desactivación.
- limits.evaluate: consulta preventiva de una wallet.
- alerts.view: lista, evidencia e historial.
- alerts.review: cambio de estado con motivo.
- reconciliation.view: corridas y diferencias observadas.
- reconciliation.run: ejecución e idempotencia.
- reconciliation.resolve: registro de revisión de diferencias.

Todos estos permisos se consultan con walletId=null: los endpoints administrativos abarcan datos institucionales y requieren una concesión global. Un permiso contextual de negocio o wallet no permite consultar toda la institución. No se consulta User.roles ni se utiliza un scope OAuth como permiso de sesión. Cuando se integre el contrato confiable de Módulo 1, basta implementar el adaptador existente, incluyendo estas acciones globales.

## Límites

Crear límites globales, por tipo de wallet, propietario o rol. Permite operación, periodo, métrica de monto/conteo, umbral, acción bloquear/alertar, moneda, fechas de vigencia y activación. Los campos que definen qué se mide permanecen inmutables en edición; para cambiarlos se crea otro límite. El backend rechaza combinaciones inválidas, por ejemplo conteo por operación.

Toda creación/edición web exige motivo no vacío. El actor proviene de la sesión user:<ID>, aunque el cliente mande actor_id. El historial paginado conserva antes/después, motivo, actor, fecha y correlación. La edición envía una huella revision del registro leído y la comprueba bajo bloqueo SQL: si el registro cambió se devuelve 409 y se debe volver a cargar la lista. No se añade una columna de versión.

La evaluación preventiva reutiliza FinancialLimitService y no mueve dinero, reserva saldo ni registra alertas. No garantiza aceptación posterior. Límites por rol siguen dependiendo de FinancialRoleProvider: si el contrato no está integrado se muestra la respuesta 503; no se omite el control.

## Alertas

Filtros por estado, wallet, resultado y correlación. Consulta evidencia y historial. Permite pasar a revisión, resolver o descartar con nota obligatoria y actor de sesión. Los estados finales no se reabren; las transiciones las decide el servicio existente. Consultar y revisar son permisos separados. Importes sin moneda en la respuesta se muestran en centavos para evitar asignar una moneda supuesta.

## Conciliación

Filtros por fecha contable y estado. Corridas globales o restringidas a UUID de wallets. Header Idempotency-Key obligatorio, conservado para reintentos de un formulario. La corrida se registra con trigger_source=INTERFAZ y usuario real; una clave ya perteneciente a otro actor/origen se rechaza. Las reglas existentes controlan fecha, ámbito, reintentos y bloqueo de ejecución concurrente.

Se muestran estado, diferencias nuevas/recurrentes, actor, estado de caja y fallos. El detalle pagina las diferencias observadas, incluidas las conocidas de otras corridas. Resolver una diferencia exige nota y permiso específico; debe haber sido observada por la corrida indicada. No ajusta saldos ni borra evidencias. Una diferencia observada después de su resolución se señala explícitamente.

Caja 2.8 sigue NO_INTEGRADA hasta implementar CashReconciliationSource. El scheduler y los workers no se modifican en este bloque. Estas dependencias y el contrato humano de roles siguen pendientes; esta entrega no declara cerrado todo el requerimiento 2.10.

## Cambios y verificación

Once archivos: cuatro controladores web, trait de actor de sesión, middleware de permisos, rutas web, acceso desde Dashboard, Controls.vue, siete pruebas y este documento. Los controladores web reutilizan validaciones, DTO y servicios existentes; la API OAuth queda intacta. Ningún secreto se envía al navegador.

Apply-Changes.ps1 verifica hashes del corte base, ejecuta php -l antes de copiar y conserva respaldo. Verify-Changes.ps1 comprueba base de pruebas, ejecuta las siete pruebas nuevas y seguridad de roles, toda la suite financiera (incluido 2.7), conciliación diagnóstica, rutas y npm run build. Para esta entrega se exige campus_digital_financial_testing, como en las pruebas SQL Server existentes.

Las pruebas cubren autenticación, denegación por defecto y roles heredados, permisos globales frente a contextuales, separación de las ocho acciones, edición obsoleta, auditoría de actor/motivo, evaluación sin movimientos y dependencia no disponible, evidencia/estados finales, conciliación idempotente y resolución sin ajustar dinero. El falso autorizador existe únicamente en el archivo de pruebas.

Validación aquí: scripts y templates Vue compilados con el compilador del proyecto, imports y campos contrastados contra fuentes, servicios base sin modificaciones y manifiesto del ZIP verificado. PHP, SQL Server y MongoDB no están disponibles en este entorno; pruebas reales, lint y build completos deben ejecutarse con Verify-Changes.ps1 en Windows. No se afirma que hayan pasado antes de recibir la salida.

Después de verificar, abrir /finanzas/controles con sesión real y comprobar los estados sin autorización. La revisión visual de los controles habilitados requiere el adaptador real; no se proporciona un bypass de producción.
