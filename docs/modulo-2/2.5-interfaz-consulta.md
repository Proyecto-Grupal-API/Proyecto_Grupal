# 2.5 — Consulta de bonos en la interfaz

Base: `4c45d4b`. Primer bloque de interfaz del 2.5: consulta del titular, sin acciones administrativas.

## Comportamiento

En Finanzas aparece **Mis bonos**, con un listado paginado de 12 registros, filtro por tipo, saldo de bonos vigentes agrupado por moneda, detalle de condiciones y restricciones, e historial paginado de 20 movimientos. Se incluyen emisiones, consumos, cancelaciones, vencimientos y devoluciones cuando existen en el ledger del bono.

El resumen de bonos no se suma a la wallet. Excluye bonos fuera de vigencia, cancelados, agotados y sin saldo. Un saldo vigente no garantiza que pueda usarse en cualquier compra: se mantienen las restricciones, combinabilidad y uso parcial del servicio existente. Los bonos vencidos conservan su saldo registrado visible en el historial y detalle, con advertencia de que no pueden utilizarse en nuevas compras.

El estado mostrado se deriva de vigencia y saldo; `recorded_status` conserva el estado persistido. Las consultas no llaman a `expireIfNeeded`, no cambian modelos y no crean movimientos. Las fechas se muestran en la zona financiera configurada.

## Acceso

Se conserva el grupo web existente: autenticación, correo verificado, sesión activa y seguimiento de dispositivo. El beneficiario se obtiene del identificador del usuario autenticado; el cliente no puede seleccionar otra cuenta mediante query strings. Se admiten `USER` y `STUDENT` únicamente cuando `beneficiary_id` coincide con ese identificador, en coherencia con el identificador de propietario usado por PurchasePaymentService. No se buscan coincidencias por correo, matrícula, nombre o rol.

Si un emisor externo identifica STUDENT mediante un identificador distinto del usuario, esos bonos no aparecen hasta definir e implementar el mapeo autorizado en el contrato de identidad. No se infiere una relación ni se reutiliza una matrícula como prueba de titularidad.

Bono ajeno y bono inexistente devuelven 404, tanto para detalle como para historial. La autoasignación de un rol administrador no cambia el acceso. Las respuestas no exponen identificadores de actores ni del emisor. No se modifica la API OAuth existente de consulta por UUID.

Rutas:
- GET `/finanzas/bonos`: pantalla Inertia.
- GET `/finanzas/bonos/{bonusId}`: detalle JSON para la pantalla.
- GET `/finanzas/bonos/{bonusId}/history`: historial JSON paginado para la pantalla.

Son endpoints web con sesión; no constituyen una nueva API de servicios. El 2.5 conserva su BonusController y servicios de dominio actuales.

## Verificación

Apply valida hashes del corte base, sintaxis PHP y carga de rutas, con respaldo y restauración de archivos si falla el arranque. No modifica .env ni instala migraciones nuevas.

Verify comprueba sintaxis, ejecuta BonusWebTest, BonusServiceTest, PurchasePaymentServiceTest y PurchaseRefundServiceTest en `campus_digital_financial_testing`, después la suite financiera completa y la compilación del frontend. Conserva/restaura las variables de proceso de su verificación. No borra datos de desarrollo ni activa un scheduler de pruebas.

Las nuevas pruebas comprueban autenticación, aislamiento entre titulares, resistencia a query strings manipuladas y roles autoasignados, condiciones y restricciones, agrupación por moneda, vigencias sin cambios de saldo, filtros y paginación del listado y del historial. La ejecución real de PHP/SQL Server y Vite debe confirmarse en el equipo Windows.
