# 2.7 — Interfaz conectada de retenciones, devoluciones y reversos

Base: a580dbf, después de aplicar y verificar el bloqueo de autoasignación de roles. No reemplaza ese arreglo ni habilita el simulador de roles.

## Acceso y comportamiento

Ingresar con sesión válida, abrir Finanzas y pulsar Retenciones y devoluciones. Ruta: /finanzas/ajustes. Conserva el layout y los colores de Campus Virtual.

La página muestra datos reales de la wallet USER perteneciente al ID de la sesión: disponible, retenido, retenciones, solicitudes de devolución, compras completadas y operaciones. Se muestran hasta 50 registros recientes por listado; esta entrega no incorpora búsqueda histórica general ni paginación de todos esos listados. El historial de políticas sí está paginado.

El propietario puede solicitar una devolución simple o de compra con reparto explícito entre wallet y bonos. Las solicitudes no mueven dinero; las reglas financieras existentes deciden importes, saldos, idempotencia y estados. Las compras de un solo bono usan el reparto histórico de PurchasePayment.bonus_id; las de varios bonos usan sus líneas. No se convierte un bono en efectivo.

La interfaz muestra los formularios y controles de aprobación/rechazo, ejecución de devolución, confirmación de recuperación externa de retiro, liberación/captura de retenciones, reversos y administración/historial de políticas. Están conectados a rutas web que reutilizan los servicios financieros y verifican los permisos en el servidor; ocultar o deshabilitar un botón no es la protección.

La creación de nuevas retenciones sigue siendo una operación del flujo comercial y de la API de servicio, no un formulario libre para reservar fondos de cualquier wallet. La captura comercial con contrapartida del negocio queda pendiente de integración, como se documentó en los bloques anteriores.

## Autorización separada y continuidad

FinancialWebAuthorizer::allows(userId, action, walletId?) es el punto de integración para autorización humana. PendingFinancialWebAuthorizer devuelve false para acciones administrativas y no consulta User.roles. Estos roles heredados pudieron ser autoasignados; no se usan como prueba de autoridad.

Acciones: adjustments.view (consultar otra wallet), refund.review, refund.execute, refund.recover, hold.release, hold.capture, transaction.reverse, policy.view y policy.manage. Para un reverso se exige permiso sobre todas las wallets involucradas. Los permisos de políticas son globales y se consultan sin wallet. El futuro adaptador deberá validar usuario activo, asignaciones vigentes, ámbito y separación de responsabilidades según el contrato de Módulo 1.

El adaptador está registrado en AppServiceProvider. Cuando exista el contrato confiable, se cambia ese binding por la implementación real: no se reemplazan rutas, formularios ni servicios. Tras recargar la misma página, las capacidades habilitarán los controles autorizados. No se introduce un bypass por email, por .env o por rol admin heredado.

## API consumida por la interfaz

Las rutas bajo /finanzas/ajustes constituyen la API web de la interfaz y usan sesión, protección CSRF/origen, verificación y middleware de sesiones/dispositivos existentes. Son distintas de la API OAuth de servicios /api/v1/financial: no se introducen secretos de cliente en el navegador ni se sustituyen los scopes de servicios por cookies.

Todas las mutaciones obtienen el actor como user:<ID de sesión>. El cliente no puede elegir actor ni propietario. Solicitudes propias comprueban la pertenencia de la wallet en el servidor; pagos/compras ajenos se rechazan. Acciones administrativas invocadas manualmente también reciben 403 mientras el adaptador esté pendiente.

Las operaciones monetarias envían Idempotency-Key. El formulario conserva su clave durante reintentos de la misma solicitud y evita doble envío mientras procesa. Los motivos/actores de transacciones web quedan registrados en metadata web_action_reason/web_actor_id dentro de una transacción SQL junto con el servicio. Reintentar la misma transacción con otro motivo o actor genera conflicto. La auditoría usa una instancia fresca del modelo para conservar el estado del observer de alertas del 2.10.

Los importes escritos en pesos se convierten con dos decimales a centavos; los servicios siguen usando enteros. La interfaz muestra errores de validación o conflicto y vuelve a cargar los datos al confirmar una acción. Ninguna simulación muestra una aprobación financiera falsa.

## Aplicación y verificación

Extraer ZIP y ejecutar Apply-Changes.ps1 -ProjectPath. Comprueba hashes del corte, hace lint antes de copiar y crea respaldo. No altera .env ni añade migraciones.

Verify-Changes.ps1 -ProjectPath ejecuta nueve pruebas nuevas de web más las cinco pruebas de seguridad de roles, después toda la suite financiera, conciliación diagnóstica, listado de rutas web y API, npm run build y git diff --check. Conserva el ajuste de aislamiento OAuth en tests/TestCase.php.

Se compiló el script y template de ambos componentes Vue usando el compilador presente en el ZIP del proyecto; se revisaron imports, delimitadores y manifiesto. PHP, SQL Server y MongoDB no están disponibles aquí: la ejecución real de pruebas y la compilación completa quedan a cargo del verificador en el equipo del proyecto. No se afirma que ya hayan pasado.

Las pruebas comprueban autenticación, propiedad de datos, wallet ausente, rechazo de roles heredados, solicitud e idempotencia, denegación de acciones manuales, reparto de compras con bonos y funcionamiento de políticas/aprobación/ejecución mediante un adaptador falso exclusivo de testing. Ese adaptador no se instala en producción.

Después de verificar, revisar visualmente /finanzas/ajustes con una cuenta real: estados vacíos, consultas de la wallet propia y controles administrativos deshabilitados. Mantener schedule:work abierto durante desarrollo si se desean liberaciones automáticas; el despliegue permanente del scheduler sigue pendiente.
