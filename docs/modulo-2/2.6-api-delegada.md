# 2.6 - API de transferencias con delegación de identidad

Base 44c57bb. Complementa la interfaz ya verificada (440 pruebas). Este nuevo bloque requiere ejecutar su verificación; no se afirma que haya sido probado con PHP/SQL/Mongo en el entorno de preparación.

## Responsabilidades independientes

TransferDelegationProvider resuelve una autorización verificable del usuario. ResolveTransferDelegation es middleware de transporte y no ejecuta dinero. TransferRecipientProvider identifica al destinatario. TransferAuthorizationProvider controla permisos de envío, recepción y administración. StudentTransferConfirmationService prepara/expira/cancela/confirma, StudentTransferPolicyService administra políticas versionadas y StudentTransferService mueve dinero atómicamente.

StudentTransferJsonController contiene las acciones JSON compartidas que antes estaban en StudentTransferWebController. Web deriva el actor de la sesión y conserva la página Inertia. StudentTransferApiController deriva el actor exclusivamente del atributo que establece el middleware de delegación. No se fabrica una sesión ni se asigna un usuario artificial al guard. Ambos transportes invocan exactamente las mismas reglas; débito, crédito, ledger y confirmación siguen siendo una transacción contable conjunta.

No cambia servicios contables, migraciones, montos, políticas guardadas, roles, .env ni pantalla Vue. La compilación se ejecuta como comprobación de compatibilidad.

## Endpoints

Base /api/v1/financial/student-transfers. Todas las rutas requieren token OAuth de servicio, scope específico y delegación del usuario.

| Verbo | Ruta | Scope adicional | Acción de delegación |
| --- | --- | --- | --- |
| GET | /records | financial:transfer:read | history |
| GET | /confirmations | financial:transfer:read | pending |
| GET | /confirmations/{confirmationId} | financial:transfer:read | preview |
| POST | /confirmations | financial:transfer:prepare | prepare |
| POST | /confirmations/{confirmationId}/confirm | financial:transfer:confirm | confirm |
| POST | /confirmations/{confirmationId}/cancel | financial:transfer:cancel | cancel |
| GET | /{transferId} | financial:transfer:read | detail |
| GET | /policy | financial:transfer:read | policy-read |
| GET | /policy/history | financial:transfer:policy:manage | policy-history |
| PATCH | /policy | financial:transfer:policy:manage | policy-update |

Preparar recibe identity_method USER_ID/ENROLLMENT/QR, recipient, amount_cents entero, kind TRANSFERENCIA/REGALO y concept opcional. Preparar y confirmar requieren Idempotency-Key. Confirmar solo recibe confirmed=true. Las claves no conceden autorización y no permiten cambiar monto/destinatario/concepto. Cancelar no deshace envíos completados. Listados paginados de 20, solo dueño/participantes según el endpoint. Administración sigue exigiendo canManagePolicy aunque el scope de servicio permita llegar al controlador.

Se exige X-User-Authorization (prueba opaca, no ID de usuario). sender_id, actor_id, user_id y source_wallet_id en los parámetros de solicitud se rechazan con 422. El emisor y su wallet provienen exclusivamente de identidad verificada. No se expone el saldo del destinatario. La política se modifica con expected_version y reason, conserva auditoría de usuario y snapshots del servicio.

30 solicitudes por minuto por cliente de servicio y acción del controlador (independiente de la IP del proxy y de otras acciones). El límite se comprueba antes de resolver la prueba. La correlación utiliza el middleware existente. Conservar TLS en despliegue y no registrar Authorization ni X-User-Authorization en proxies o registros de aplicación.

## Contrato para el Equipo 1

TransferDelegationProvider::resolve(clientId, proof, action, requestDigest): string devuelve únicamente el ID de cuenta real de 24 caracteres. La implementación debe verificar emisor/firma confiable, audiencia, expiración, cliente OAuth autorizado para esa delegación, acción exacta, estado de cuenta/sesión y revocación. La confirmación debe demostrar consentimiento explícito a la preparación inmutable que identifica la ruta, no solo la identidad del usuario. Nunca confiar en un campo sender_id ni en roles autoasignados.

requestDigest es SHA-256 de JSON UTF-8 sin escapar barras/Unicode, con este orden de campos: method en mayúsculas, path con / inicial, input (parámetros ya normalizados por Laravel, objetos ordenados recursivamente por claves SORT_STRING; listas conservan orden) e idempotency_key normalizada trim/minúsculas o cadena vacía. Se usa JSON_THROW_ON_ERROR. El método ResolveTransferDelegation::digest es la referencia ejecutable. El Equipo 1 debe acordar esta canonicalización antes de emitir pruebas. No reutilizar pruebas para datos, ruta, cliente, acción o clave diferentes. Reintentos idénticos deben seguir permitiendo la idempotencia contable; confirmar un envío ya ejecutado no duplica dinero.

Proof inválida/expirada/revocada debe lanzar UnauthorizedHttpException (401); dependencia indisponible FinancialDependencyUnavailableException (503). El middleware comprueba el formato del ID resultante y falla 503 si el contrato devuelve una identidad malformada. No se guardan pruebas crudas en SQL ni se escriben en logs propios. Un fallo inesperado no permite continuar al controlador.

PendingTransferDelegationProvider devuelve 503 por defecto. NO incluye emisor o validador real de pruebas ni usa JWT inventados para habilitar producción. Mientras no se conecte el contrato, los endpoints están registrados pero no pueden operar con delegación real. Sustituir únicamente este binding y conectar el proveedor de permisos confiable; la interfaz continúa utilizando su sesión habitual. Las pruebas usan un doble del contrato expresamente solo para pruebas.

La limitación real de QR documentada en 2.6-confirmacion-interfaz se mantiene: IdentityService llama displayIdentity() ausente en User. Esta API no corrige ni certifica ese servicio del Equipo 1. No incluye Docker; continúa pendiente del bloque de despliegue.

## Respuestas y verificación

401: token/prueba ausentes o inválidos; 403: scope o permiso del dominio ausente; 404: solicitud/operación ajena o inexistente; 422: validación/clave/identidad falsificada; 409: estado, saldo, límites o solicitud idempotente incompatible; 429: tasa; 503: delegación pendiente o identidad indisponible. Primera preparación/ejecución 201, replay 200. El campo replayed conserva el comportamiento del transporte web.

StudentTransferApiTest incluye nueve casos de token+delegación+adaptador pendiente, diez rutas con scopes separados, regalo confirmado sin duplicación, aislamiento entre titulares, vínculo de prueba a acción/payload/ruta/clave, identidad malformada y campos de emisor falsificados, scope administrativo versus permiso real cancelación/clave requerida y tasa independiente por acción. Firma, expiración y revocación del futuro contrato se deben probar en la integración real; las pruebas actuales usan un doble verificable, no certifican criptografía externa.

Verify-Changes.ps1 valida PHP, configuración, pruebas nuevas+web+dominio, toda la suite financiera, rutas web/API, Vite y git diff --check. No hay migración nueva. No omitir las pruebas web: comprueban que extraer el transporte JSON conserva el funcionamiento previo.
