# 2.8 — Segunda autorización configurable de caja

Base de integración: `73e100d`. Esta entrega agrega reglas para recargas (`TOPUP`) y retiros (`WITHDRAWAL`) en efectivo; no cambia las reglas de ajustes físicos, cierres, recuperaciones ni reversos.

## Regla y configuración

Una regla se identifica por asociación externa, operación y moneda. Tiene `enabled`, `threshold_cents` positivo y `version`. El umbral es inclusivo. Si no hay regla registrada, o está desactivada, no se exige supervisor. No se siembran umbrales de producción ni se habilitan permisos automáticamente.

La pantalla `/finanzas/caja/autorizaciones` permite consultar, configurar y revisar según permisos. Usa la sesión autenticada y conserva CSRF. El umbral se introduce en centavos; 10000 equivale a 100.00 unidades de la moneda indicada. La edición exige la versión consultada, clave de idempotencia y motivo. El historial guarda estado anterior, posterior, actor y fecha. Los cambios concurrentes se rechazan; un reintento válido conserva la respuesta original incluso después de cambios posteriores.

## Solicitud y decisiones

Al solicitar la confirmación del titular se captura la regla aplicable, incluyendo versión 0 cuando todavía no existe. Si corresponde, se marca `supervisor_required` y la decisión inicia en `PENDING`. Las solicitudes previas a esta migración conservan su comportamiento: no se les impone autorización retroactivamente. Cambiar o desactivar la regla no elimina la exigencia de una solicitud ya creada; debe cancelarse y generarse una nueva cuando proceda.

El supervisor revisa la solicitud desde su propia sesión. No puede ser el principal solicitante/operador ni el titular. Tokens de servicio no pueden autorizar como personas. Se comparan identidades canónicas de los principales disponibles (`user:<id>` y `service:<sub>`); no se infiere una persona detrás de una cuenta de servicio. La integración de identidades y delegaciones de otros módulos debe conservar estas restricciones.

La autorización administrativa y la del titular pueden darse en cualquier orden. Ambas deben estar vigentes al ejecutar. Se usa la caducidad de la confirmación existente (por defecto 300 segundos, configurable entre 60 y 900). El rechazo administrativo termina la solicitud sin mover dinero. Las decisiones guardan supervisor, motivo y fecha, no admiten sobrescritura y aceptan el reintento exacto del mismo actor y motivo.

Al ejecutar se vuelve a comprobar el permiso del supervisor en esa asociación. Su revocación bloquea solicitudes no consumidas. No se amplían los permisos del operador ni se le permite ejecutar turnos ajenos. Una ejecución confirmada genera un solo movimiento y un comprobante con la política y la segunda autorización; el ledger también conserva esta evidencia. Si falla la liquidación, la confirmación vuelve a estar disponible para reintentar, mientras la aprobación ya registrada se conserva. El reintento de una operación consumida con su clave original retorna el resultado previo incluso si después vence o se revoca el permiso; nunca vuelve a mover dinero.

## Permisos e integración pendiente

Se reutiliza `CashAuthorizationProvider`; `PendingCashAuthorizationProvider` continúa denegando todo. No se usan roles autoasignados ni banderas para saltar permisos. Los nombres de acción nuevos son:

| Acción de contrato | Uso |
| --- | --- |
| `approval_read` | Consultar reglas, historial y solicitudes de la asociación |
| `approval_manage` | Crear/modificar/desactivar reglas |
| `approval_review` | Aprobar/rechazar como supervisor humano independiente |

La integración futura de roles debe otorgar las acciones correspondientes. Gestionar reglas no otorga automáticamente permiso para aprobar, consultar u operar. La interfaz de administración requiere `approval_read` y `approval_manage`; la de revisión, `approval_read` y `approval_review`.

API, bajo `/api/v1/financial/cash/associations/{associationId}`:

| Método y ruta | Scope OAuth y acción de asociación |
| --- | --- |
| GET `/approval-policies` | `financial:cash:approval:read` + `approval_read` |
| POST `/approval-policies` | `financial:cash:approval:manage` + `approval_manage` |
| GET `/approval-policies/history` | `financial:cash:approval:read` + `approval_read` |
| GET `/approval-requests` | `financial:cash:approval:read` + `approval_read` |

No existe un endpoint OAuth de aprobación humana. Las decisiones se envían a POST `/finanzas/caja/asociaciones/{associationId}/approval-requests/{confirmationId}/{approve|reject}` con sesión y `approval_review`. El actor siempre se obtiene del servidor. Todas las consultas son paginadas y se limitan a la asociación autorizada; conocer un UUID no permite acceder a solicitudes ajenas.

Los métodos internos de `CashSettlementService` usados por código confiable siguen existiendo para pruebas e integración. Los endpoints externos de recargas y retiros usan exclusivamente `settleConfirmed`, que exige estas autorizaciones. Nuevas integraciones no deben exponer los métodos internos como alternativa al flujo confirmado.

## Verificación

`CashSupervisorApprovalTest` cubre política versionada, historial, reintentos, versiones obsoletas, umbral inclusivo, operación/moneda/asociación, instantáneas, separación de actores, confirmación del titular, rechazo/vencimiento/revocación, rollback, recargas, ausencia de duplicados y permisos HTTP/OAuth. Los datos se limpian únicamente en la base financiera de pruebas y con prefijos de prueba.

Ejecutar la migración y `Verify-Changes.ps1`; este valida sintaxis PHP, arranque de rutas, pruebas específicas, suite financiera, conciliación y compilación Vue. La compilación local de los componentes se comprobó en el entorno de preparación; las pruebas Laravel/SQL Server se ejecutan en el equipo de desarrollo.
