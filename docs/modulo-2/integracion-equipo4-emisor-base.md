# Base del emisor de estados de pago a Equipo 4

Entrega incremental, no integración de cobro terminada. No modifica roles, rutas API ni servicios financieros existentes. No envía automáticamente eventos y viene desactivada. El receptor de Equipo 4 requiere correcciones antes de probar devoluciones reales.

Contrato implementado por el emisor: POST /api/equipo4/webhooks/payment-status, JSON UTF-8 sin BOM y HMAC-SHA256 de timestamp|POST|path|sha256(body), hex minúsculas. IDs por evento, versión incremental por intención, refund_id requerido en REFUNDED/PARTIALLY_REFUNDED. Misma identidad y cuerpo en todos los intentos; timestamp y firma nuevos. amount se serializa como número decimal desde centavos sin float. Solo MXN. Items son snapshot financiero de origen confiable: esta validación estructural no certifica venta, precios, inventario ni cantidades devueltas acumuladas.

El servicio PaymentEventOutbox::record(sourceReference, payload) requiere estar dentro de la transacción sqlsrv del cambio financiero real. No puede invocarse como prueba de un cobro inexistente. La referencia de origen debe identificar UN cambio financiero inmutable: por ejemplo un ID de pago completado o un ID de devolución; nunca una clave nueva por cada retry HTTP. Misma referencia/cuerpo devuelve mismo event_id; cambios dan conflicto. La intención queda vinculada a pedido y negocio. Creación concurrente inicial de una intención puede provocar conflicto SQL/deadlock: el llamador debe revertir/reintentar su transacción completa con la misma idempotencia. No se descarta silenciosamente el evento.

Outbox y pago se confirman o revierten juntos. La entrega se ejecuta FUERA de esa transacción mediante financial:team4-deliver. Lease SQL de 120 segundos y estado por evento evitan que dos workers reclamen el mismo evento al mismo tiempo. Tras caída se reintenta el mismo evento; exactamente una aplicación del efecto requiere el receptor idempotente corregido. Los eventos de una intención se envían en orden; REVIEW o EXHAUSTED bloquean los siguientes hasta revisión operativa. No existe comando de forzar PAID ni de marcar recibido sin evidencia.

202 solo se admite con received=true booleano y payment_event_id de texto. Error 5xx, conexión y 429: retry. 401/403/409/422, respuestas inesperadas o ACK inválido: REVIEW. Redirects no se siguen. Backoff 5s/30s/5min/30min/2h, cinco reintentos después del inicial (seis intentos totales): propuesta pendiente de acuerdo. No guarda cuerpo remoto, tokens, firma o secreto en diagnósticos. Intentos interrumpidos quedan con finished_at nulo como evidencia; el lease permite recuperarlos.

Activación futura: FINANCIAL_TEAM4_WEBHOOK_ENABLED=true, FINANCIAL_TEAM4_WEBHOOK_URL y FINANCIAL_TEAM4_WEBHOOK_SECRET privados. URL de ruta exacta; HTTPS fuera de local/testing. No cambiar el flag antes de probar receptor y hooks. En Docker localhost apunta al contenedor actual: acordar el nombre de servicio de destino. El comando es un lote finito; NO es un worker que permanece escuchando. Para los retrasos de 5 y 30 segundos se necesita invocación frecuente o un job runner; una llamada por minuto añade latencia. No se registra scheduler ni se modifica la cola existente en esta base.

Pendiente: conectar record a los servicios de cobro/estado/devolución con el contrato de pedido de Equipo 3, verificar autorización del pagador, pruebas conjuntas y política/flujo operativo de recuperación manual de REVIEW/EXHAUSTED. No se conecta a recargas/retiros de Caja, que no son ventas de Marketplace. No se crea un endpoint de publicación genérico accesible a otros módulos.
