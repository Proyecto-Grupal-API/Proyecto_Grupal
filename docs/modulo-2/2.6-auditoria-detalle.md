# 2.6 - Auditoría, contratos de cuentas y detalle en interfaz

Base: 245fb12 (API delegada con limitador corregido). Incluye cambios de dominio, API JSON compartida e interfaz Vue. No concede permisos ni modifica .env, roles o código del Equipo 1.

## Responsabilidades

- TransferAccountProvider::assertActive(userId) valida cuentas en lugar de consultas directas de User dentro de StudentTransferService y StudentTransferConfirmationService. Module1TransferAccountAdapter usa las entidades disponibles, rechaza cuentas inexistentes/inactivas/no verificadas y transforma caídas de consulta en FinancialDependencyUnavailableException. Puede sustituirse por el contrato oficial sin modificar las pantallas. Las validaciones durante la ejecución se mantienen dentro de la transacción SQL para revalidar antes de mover; una llamada remota futura deberá tener timeout acotado y evitar esperas largas bajo bloqueo.
- TransferSessionContextProvider::resolve(userId, registeredSessionId) obtiene únicamente referencias del registro de sesión confiable del módulo 1, nunca el secreto de sesión Laravel. El adaptador comprueba dueño y revocación; no atribuye sesiones ajenas/revocadas. Estos datos son evidencia adicional y no conceden autorización. La autenticación/session.active y los permisos existentes siguen controlando acceso.
- TransferAuditContext es un objeto inmutable de evidencia. TransferAuditContextResolver obtiene el canal, cliente OAuth, IP y correlación del servidor; para web resuelve la referencia cd_session_id de la sesión del servidor. No utiliza actor/device/session enviados en body o cabeceras arbitrarias.
- StudentTransferQueryService separa consulta/listado/detalle de la ejecución monetaria. Aplica aislamiento por participantes, filtros kind/direction y paginación de 20. Carga las transacciones del listado en una consulta conjunta para evitar una consulta adicional por cada fila normal.

## Auditoría persistida

La migración 040000 agrega audit_context a student_transfers y student_transfer_policy_changes, y preparation_audit, confirmation_audit, cancellation_audit a student_transfer_confirmations. Son JSON en columnas text nullable, compatibles con SQL Server. No reescribe registros históricos ni inventa evidencia pasada.

Se guarda canal WEB/API/INTERNAL, client_id validado en API, IP obtenida por Request (según la configuración vigente de proxies), correlación y referencias de sesión/dispositivo cuando se verifican. La API actual únicamente delega un user ID: dispositivo/sesión quedan null con NOT_PROVIDED hasta que el contrato oficial aporte esa evidencia. No se adivinan IDs a partir de User-Agent, X-Device-Id, body, cookies secretos ni JWT del cliente. El IP de API corresponde a la solicitud del servicio; no se atribuye como IP del dispositivo del estudiante.

Preparación y confirmación conservan contextos diferentes. StudentTransfer y FinancialTransaction.metadata guardan el contexto de la ejecución exitosa. El callback guarda confirmation_audit en la misma transacción contable: si falla, se revierte dinero, ledger, StudentTransfer y auditoría de confirmación, manteniendo la preparación y su clave de retry. Un reintento exitoso conserva la primera evidencia registrada; una cancelación repetida no cambia la evidencia original. Los cambios de política registran contexto junto al actor/motivo/before/after/versión.

Llamadas internas existentes siguen compatibles mediante parámetros opcionales al final; cuando no se proporciona contexto se marca INTERNAL y no se simula una sesión web. No se registra la prueba X-User-Authorization, token Bearer, clave de sesión nativa o código QR. La auditoría privada NO se expone completa a estudiantes ni al destinatario. Una futura consulta administrativa global necesita permiso específico del contrato oficial; no se reutiliza el permiso de editar política para inventar ese acceso.

## Interfaz y API

Finanzas > Transferencias y regalos ahora permite filtrar historial por TRANSFERENCIA/REGALO y SALIDA/ENTRADA. Los filtros conservan aislamiento por participantes y se validan en servidor. El botón Ver detalle carga la ruta existente, desplaza la página a la sección y muestra monto, concepto, participantes, fecha, referencia contable, versión y límites aplicados, canal/correlación, fecha de confirmación y el movimiento de la wallet del participante. No muestra balances del destinatario ni datos privados de dispositivo/IP/sesión.

GET /finanzas/transferencias/{transferId} y GET /api/v1/financial/student-transfers/{transferId} comparten el detalle. Los listados /records aceptan kind y direction, además de page. Se mantienen las mismas diez rutas web y diez rutas externas; no se añaden rutas nuevas.

Si FinancialTransaction fue revertida mediante 2.7, el detalle muestra REVERTIDA, la referencia del reverso y conserva executed_status=COMPLETADA como dato de ejecución histórica. No ofrece cancelación libre ni botón de reverso para usuarios comunes. Un registro anterior con auditoría null se presenta como no registrado, sin imputar una evidencia retrospectiva.

Se corrige el concepto literal "0": permanece como texto en preparación, StudentTransfer, metadata y consulta; únicamente una cadena vacía se convierte en null.

## Integraciones que siguen pendientes

TransferAuthorizationProvider y TransferDelegationProvider continúan cerrados hasta integrar roles y delegación reales. QR sigue sujeto a la limitación displayIdentity() del Equipo 1 documentada anteriormente. El adaptador de destinatarios ahora devuelve 503 si falla la consulta de identidad/Mongo, sin crear preparación ni mover dinero. En web, una caída de middleware previo del Equipo 1 (por ejemplo seguimiento de dispositivo) todavía puede impedir llegar a este control financiero; este bloque no modifica esos middleware. No se implementa validación criptográfica externa en un doble de pruebas.

La política económica global y sus valores continúan iguales. Permite cambios autorizados por versión; las restricciones adicionales 2.10 siguen vigentes. No se agregan excepciones de rol que permitan superar el máximo global sin definir la política institucional correspondiente. Docker y pruebas de concurrencia con procesos reales continúan pendientes del bloque transversal; las pruebas de mutex/fallos ya existentes no equivalen a una prueba de carga simultánea real.

## Pruebas y aplicación

StudentTransferAuditTest añade 11 ejecuciones (10 declaraciones, reversión parametrizada para ambos tipos): web con preparación/confirmación separadas y concepto cero; cliente API confiable/dispositivo no atribuido; caída de contrato de cuentas y retry; sesión propia versus ajena/revocada; privacidad del detalle; filtros web/API; reversión de transferencia y regalo confirmados sin duplicación; auditoría de cancelación/política; compatibilidad de llamadas internas y registros históricos; rollback ante fallo de evidencia de confirmación.

Las pruebas usan cuentas con correos UUID, wallets propias de la prueba y limpieza de referencias contables, usuarios, sesiones y dispositivos del fixture; no tocan cuentas reales. La base SQL obligatoria es campus_digital_financial_testing. CSRF se deshabilita solo en estas pruebas para probar dominio/autorización; en producción permanece activo.

El entorno de preparación no tiene PHP, SQL Server/MongoDB ni compilador Vue. Se comprobó sintaxis JavaScript extraída, coherencia de cambios, integridad del ZIP/hashes y whitespace. Verify-Changes.ps1 ejecuta PHP lint, migración testing (y desarrollo con -MigrateDevelopment), las nuevas pruebas y regresiones 2.6/2.7/ledger, la suite financiera completa, rutas y npm build. No se afirma que este nuevo bloque haya aprobado pruebas hasta recibir la salida real.
