# 2.7 — Reversos administrativos

Base: commit bed3d32, posterior a 264 pruebas financieras aprobadas y a la corrección de UUID de WalletHoldController.

## Comportamiento

- Reverso completo de un pago simple PAGO, sin PurchasePayment asociado, o transferencia con exactamente dos movimientos opuestos, distintas wallets y misma moneda.
- Original COMPLETADA pasa a REVERTIDA; nueva transacción REVERSO queda COMPLETADA. El ledger original se conserva y se crean movimientos compensatorios con deltas explícitos.
- No consume saldo retenido. El receptor de una transferencia debe tener saldo disponible suficiente para devolver el importe.
- Original, movimientos y wallets se bloquean dentro de una transacción SQL Server. Fallar revierte todo y permite reintentar.
- Una clave repetida exige original, responsable, motivo y estados consistentes. Otra clave no puede reversar nuevamente el original. Colisiones de claves únicas producen conflicto de negocio.
- Se rechazan retiros, recargas, devoluciones, reversos previos, compras administradas por PurchasePayment, retenciones y capturas de retenciones. Los retiros conservan su flujo de recuperación externa y devolución; las compras conservan PurchaseRefundService.
- Se rechaza un original con devoluciones pendientes, aprobadas o completadas. Una devolución rechazada libera ese impedimento.
- La corrección administrativa puede ajustar una wallet inactiva; nunca deja saldos negativos ni modifica el retenido. No es un nuevo pago.

## API

| Método | Ruta relativa a /api/v1/financial | Scope |
| --- | --- | --- |
| POST | /transactions/{transactionId}/reverse | financial:reverse |
| GET | /reversals/{reversalId} | financial:read |

POST exige Bearer, encabezado Idempotency-Key (hasta 255 caracteres) y reason con contenido (hasta 1000 caracteres). Devuelve 201 al crear y 200 al repetir. Conflictos: 409; validación: 422; falta de token: 401; permiso insuficiente: 403; UUID inexistente: 404.

El responsable se obtiene del token: service:<oauth_client_id>. El cuerpo no determina el responsable. No se otorga automáticamente el scope a ningún cliente. financial:write, financial:control y financial:refund:execute no autorizan reversos.

Un usuario normal no dispone de esta API directamente. La autorización de un administrador humano desde la interfaz dependerá del contrato de roles de Módulo 1 y del servicio autorizado que consuma esta API. Esta entrega no incorpora ese contrato ni la interfaz.

La llamada interna reverse(original, key, reason, executedBy) ahora exige responsable y motivo para ejecutar; los argumentos opcionales preservan compatibilidad de llamadas que prueban bloqueos anteriores, pero no permiten un reverso nuevo sin auditoría.

## Instalación y pruebas

1. Extraer el ZIP.
2. Ejecutar Apply-Changes.ps1 con ProjectPath. Comprueba hashes y sintaxis PHP antes de copiar; crea respaldo externo. No cambia .env ni requiere migraciones nuevas.
3. Ejecutar Verify-Changes.ps1 con ProjectPath. Corre nueve pruebas nuevas, toda la suite financiera y conciliación diagnóstica en la base de pruebas.

La entrega fue revisada estáticamente en el entorno de preparación. PHP, SQL Server y MongoDB se verifican en el equipo del proyecto; no se afirma que estas pruebas hayan sido ejecutadas antes de entregar el ZIP. Las pruebas incluyen auditoría, matriz de scopes, duplicados, insuficiencia de saldo con reintento, rechazo de operaciones externas, rollback y conciliación de pago reversado.

No se implementan reversos parciales ni cancelación de efectivo externo. Las pruebas de idempotencia son secuenciales y no equivalen a una prueba de estrés concurrente. No se integra aún la captura comercial con contrapartida del negocio.
