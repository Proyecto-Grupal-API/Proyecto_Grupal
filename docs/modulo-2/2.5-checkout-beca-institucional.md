# Checkout nativo con BECA institucional

Base 1fd63f4. Agrega un segundo medio de pago al checkout existente: una BECA presupuestada debe cubrir la compra completa. No combina bonos, no mezcla con wallet, no solicita una beca al instituto ni concede autoridad de emisión.

## Configuración y comportamiento

FINANCIAL_MARKETPLACE_INSTITUTIONAL_BECA_ENABLED=false por defecto. El instalador no modifica .env. Para habilitar posteriormente, después de pruebas y con datos institucionales legítimos, establecer true en el entorno junto con la integración Marketplace existente y limpiar config:clear. La bandera no crea presupuestos, bonos, negocios o permisos.

El comprador ve únicamente BECA propias, vinculadas a presupuesto, vigentes y suficientes. Se exige wallet USER activa de la moneda para identificación y recibos; no se crea wallet ni se debita dinero al usar BECA. El bono debe permitir el uso parcial cuando sobre saldo. Se filtran restricciones de negocio y se excluyen bonos que exigen categoría, porque el contrato actual del pedido no acredita categoría comercial. Se muestran hasta 20 opciones, ordenadas por vencimiento e ID, sin enumerar presupuestos ni revelar pagador, aprobaciones o saldos institucionales. La presentación no reserva saldo ni certifica integridad: la confirmación vuelve a comprobarlo.

La interfaz mantiene wallet como opción predeterminada y obliga a confirmar otra vez el consentimiento al cambiar de medio/bono. No cambia automáticamente de BECA a wallet si falla o no alcanza. El POST admite opcionalmente payment_method=WALLET|BECA; BECA exige bonus_id UUID y funding_review_token. Los campos anteriores consent y review_token se mantienen. Sin payment_method se conserva WALLET. No acepta importe, comprador, wallet, presupuesto o categoría aportados por el navegador.

La HMAC de revisión vincula elección de bono/presupuesto, pedido y contenido original, comprador y sesión nativa/registrada. No es un token OAuth, no se transmite a E4 y no es suficiente fuera de la confirmación activa. Almacenar una cadena authorization_reference no concede permiso.

## Autorización real del comprador

InstitutionalCheckoutConsent es un objeto scoped del contenedor Laravel. Mantiene la evidencia únicamente dentro de un callback de confirmación nativa y la elimina siempre con finally. CheckoutInstitutionalPurchaseAuthorization comprueba esa capacidad solo para purchase.pay; otros actos, incluida purchase.refund, siguen usando la denegación Pending existente. Cambia la composición del binding de compra institucional: no hay autorización positiva por IDs sueltos, flags o una referencia manual.

Dentro de la capacidad se compara el contexto completo: actor, wallet de identificación, bono, presupuesto, importe, moneda, categoría nula, pedido, negocio, artículos y referencia. También se comprueban consentimiento aceptado, método/bono del POST, firma de revisión, pedido aún pendiente e inalterado, cuenta elegible, sesión registrada propia no revocada, 2FA configurado/confirmado, contraseña reciente y cliente/negocio aún autorizados. Se revalida cuando el servicio institucional consulta autoridad, incluida la consulta posterior a sus bloqueos. No se acredita un desafío 2FA reciente. No se usan roles de emisor o administrador para gastar una BECA propia ya emitida legítimamente.

SQL y MongoDB no comparten una transacción distribuida: se revalida la sesión y el cliente antes de consumir, pero no se garantiza atomicidad con una revocación que ocurra después de la última comprobación. No se guarda una autorización positiva en caché para pagos posteriores.

## Atomicidad y bloqueos

El checkout bloquea la solicitud; para BECA no toma primero el bloqueo de wallet. El servicio institucional conserva el orden presupuesto -> bono -> wallet, y sus controles de integridad global/local, restricciones, saldo, vigencia, identidad y obligación. La compra, consumo del presupuesto, ledger de bono, obligación, enlace Marketplace, evento outbox PAID y estado PAID de la solicitud comparten la transacción SQL exterior. No se acredita dinero a wallets de negocios ni se envía HTTP a E4 al confirmar.

Una falla al guardar la solicitud final revierte toda la compra y elimina la capacidad temporal. La solicitud pendiente puede reintentarse con la misma evidencia. PAID repetido conserva el medio original; BECA verifica sesión, contraseña, elección firmada, integridad, pago original y enlace al mismo pedido, sin otro consumo ni evento. No se permite convertir una compra pagada con wallet en BECA o viceversa.

La API de preparación/consulta de pedidos conserva su contrato y payment_intent_id. El medio queda en audit_context interno; no se añade autoridad al servicio client_credentials. Estado PAID representa el pago original y no se convierte aquí en un estado de devolución: los eventos y registros de devolución existentes mantienen su ciclo propio.

## Sesión y errores

RequireMarketplaceNativeSession se ejecuta antes de device.track para impedir que una sesión registrada faltante se repare silenciosamente. Se aplica al checkout habilitado, incluida la modalidad wallet; cuando la integración está desactivada, el índice conserva su pantalla informativa. RenderMarketplaceCheckoutFailures envuelve esa guarda y sanitiza fallos Mongo, dependencias y consultas SQL. Conflictos de negocio conservan el manejo de errores de formulario; permisos/sesiones inválidos no se convierten en autorizaciones.

## Validación y límites

20 casos nuevos cubren pago real con capacidad nativa (sin un autorizador permisivo de compra), opciones propias/elegibles, invariancia de dinero al revisar, reintento y medio original, manipulación, pedido/sesión distintos, bandera desactivada, acceso directo denegado, contraseña/2FA, revocación de sesión/cliente, sesión faltante, saldo insuficiente sin fallback, presupuesto suspendido/inconsistente, rollback final y limpieza de capacidad, corrupción posterior al pago, exclusiones de bonos, propiedad aun con firma filtrada, revocación al esperar el bloqueo, expiración y contexto exacto. Presupuesto/emisión de fixtures usan autoridades falsas exclusivamente en testing; no se instalan datos ni grants en producto.

Se revisó aquí sintaxis PHP mediante parser y compilación SFC Vue. No se ejecutaron PHP/Pest, SQL Server ni build completo. Verify exige SQL campus_digital_financial_testing y Mongo campus_virtual_testing antes de TestCase; Mongo testing se reinicia por caso. Prepara únicamente las cuatro migraciones institucionales anteriores en testing, ejecuta regresión enfocada, prueba Node de importes y npm.cmd run build. No hay migraciones nuevas, llamadas reales E1 ni entrega HTTP E4. La nueva bandera se fuerza a false en el proceso verificador salvo los casos que la habilitan expresamente en config y se restaura al finalizar.

Permanecen pendientes la integración del origen comercial real con E3, la autoridad efectiva de emisión/presupuesto, cancelación administrativa institucional en interfaz, procedimientos de devoluciones vencidas y verificación/ejecución externa de liquidaciones. Este cambio no pretende resolver esos contratos.
