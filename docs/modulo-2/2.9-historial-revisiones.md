## Acceso y rutas

Se requiere sesión con correo verificado,2FAconfirmado y plaza global activa a través de LegacyCashReceiptAuthorization. Un permiso modular de lectura/configuración2.9no permite auditar registros sin contexto de asociación identificado. El actor procede siempre de la sesión. El proveedor debe sercampusyelnúcleo habilitado; no hay fallback de autorización. Si se sustituye el contrato de roles, el puerto sigue aislado.

- GET /finanzas/comprobantes-administracion/history: pantalla de historial.
- GET /finanzas/comprobantes-administracion/history/records: listado JSONdata/meta.
- GET /finanzas/comprobantes-administracion/history/{reviewId}: detalle Inertia.

Todas son consultas web, no endpoints de token de servicio. Las rutas de registros y detalle tienen throttle30/minuto. La API personal del2.9no recibe auditoría interna ni acceso global nuevo. No cambia ninguna ruta existente.

Filtros:transaction_idUUID,wallet_idUUID,reviewed_byOID24hex,pagemínimo1y máximo1000000,per_pageentre1y50. Sin filtros se muestran todas las revisiones autorizadas,20por página. Orden:fecha de revisión descendente y ID interno descendente. El ID interno SQL no se devuelve. Las fechas de evidencia se muestran explícitamenteUTC; la fecha de revisión se presenta con el formato local del navegador.

## Datos

Listado:UUIDde revisión, transacción, wallet, clasificación, cuenta revisora, motivo y fecha. No envía snapshot ni hash de evidencia en cada fila. Detalle:lo anterior más copia guardada, huellaSHA256yestado de comparación con la evidencia actual. No expone secretos de usuario, contraseña, tokens ni pruebas de delegación. La huella de clave de operación conserva el digest original, no la clave de idempotencia cruda.

Estados:
- CONSISTENT: copia y huella almacenadas coinciden; evidencia actual coincide con aprobación.
- SOURCE_CHANGED: evidencia actual diferente o incoherente; comprobante bloqueado; el detalle conserva la copia aprobada.
- SOURCE_MISSING:falta wallet/transacción original; revisión permanece disponible.
- REVIEW_RECORD_INCONSISTENT: snapshot guardado no coincide con huella; detalle advierte y consulta de comprobante se bloquea.

Se fortaleció LegacyCashReceiptEvidenceService para comprobar también la consistencia entre snapshot y huella antes de presentar una revisión en un comprobante. El detalle de auditoría no exige que la operación sea imprimible actualmente: su finalidad es poder investigar. No repara ni reescribe la evidencia al detectar cambios. El hash no es firma digital ni protege frente a alguien con control directo de la base capaz de alterar simultáneamente hash y datos.

El historial cubre las revisiones explícitas de recargas de demostración admitidas por el proceso anterior. No constituye historial de todas las operaciones financieras: los movimientos ordinarios siguen en Mis comprobantes, ledger y Caja. Tampoco agrega corrección/revocación de revisiones; los registros siguen inmutables por el modelo y no se ofrecen acciones de editar/borrar.
