# 2.7 — Políticas de retención administrables

Base: commit 8a576ca, verificado en el equipo del proyecto con 273 pruebas / 1700 aserciones y conciliación sin diferencias. La interfaz se implementará al terminar las funcionalidades de backend, como se acordó.

## Qué cambia

Las duraciones se guardan en SQL Server, no en el mapa JSON de .env. Cada tipo de operación tiene una única política con max_duration_seconds, active y version. No se crean políticas de negocio por defecto. Un tipo sin política activa no permite retenciones nuevas.

La API registra el actor del token como service:<oauth_client_id>, motivo obligatorio, correlación, fecha y snapshot antes/después. Cambiar el plazo o desactivar/reactivar incrementa la versión y agrega historial en la misma transacción. Un cambio sin efecto no agrega otra versión. No se expone borrado de políticas ni edición/borrado del historial.

Los permisos de servicios están separados: financial:read permite consultar; financial:hold-policy:manage permite crear y modificar. financial:write o financial:control por sí solos no bastan para modificar políticas. No se conceden grants automáticamente. La autorización del administrador humano desde la futura interfaz requiere el contrato de roles del Módulo 1; el navegador no debe recibir credenciales del cliente de servicio.

## API

Todas las rutas están bajo /api/v1/financial y requieren Bearer.

| Método | Ruta | Scope |
| --- | --- | --- |
| GET | /hold-policies | financial:read |
| GET | /hold-policies/{policyId} | financial:read |
| GET | /hold-policies/{policyId}/history | financial:read |
| POST | /hold-policies | financial:hold-policy:manage |
| PATCH | /hold-policies/{policyId} | financial:hold-policy:manage |

Crear: operation_type, max_duration_seconds, change_reason; active es opcional y por defecto true. operation_type debe ser un identificador en mayúsculas con letras, números o guion bajo, empezando por letra, hasta 100 caracteres. El motivo no puede estar vacío y admite hasta 1000 caracteres. El actor no se elige en el cuerpo.

Modificar: expected_version y change_reason obligatorios; max_duration_seconds y/o active. El tipo de operación es inmutable. Dos operadores que editaron la misma versión no pueden sobrescribirse: el segundo recibe 409 y debe consultar de nuevo. La edición no requiere Idempotency-Key; una repetición con versión ya reemplazada devuelve 409.

Consultar lista: filtros operation_type y active, per_page 1..200; lista e historial paginados. Respuestas conservan {data, meta}. Alta 201; consultas/cambios 200; duplicado o versión obsoleta 409; datos inválidos 422; token ausente 401; scope insuficiente 403; UUID inexistente 404.

## Duraciones y vigencia

La duración debe ser un entero positivo. FINANCIAL_HOLD_ABSOLUTE_MAX_SECONDS permite a la instalación imponer un techo adicional que un administrador de API no puede elevar. Por defecto el techo es 2147483647, exclusivamente el límite técnico de almacenamiento de SQL Server: NO constituye una recomendación de plazo ni una política de negocio. La institución puede definir un techo menor. Una configuración técnica inválida bloquea nuevas políticas/retenciones.

Al crear una retención se consulta y bloquea la política vigente dentro de la transacción SQL y se guardan policy_id, policy_version y max_duration_seconds. expires_at debe ser futuro y no superar ese máximo desde el instante de creación.

Los cambios posteriores solo aplican a retenciones nuevas. Retenciones existentes conservan su vencimiento y su copia de política. Los reintentos de creación con la misma clave/datos devuelven la retención original, aun si la política cambió o fue desactivada. Liberación, captura y vencimiento siguen sus reglas existentes; no se requiere que la política siga activa para cerrarlas.

Retenciones históricas anteriores a esta migración conservan sus fechas y quedan con procedencia de política nula. No se modifican importes, saldos ni transacciones existentes.

## Instalación y compatibilidad

1. Extraer Campus-Digital-2.7-politicas.zip.
2. Apply-Changes.ps1 -ProjectPath: revisa hashes del corte base y sintaxis antes de copiar; respalda archivos fuera del proyecto.
3. Verify-Changes.ps1 -ProjectPath -MigrateDevelopment: migra desarrollo y testing, corre 11 pruebas nuevas más 17 de retenciones existentes, toda la suite financiera, conciliación y listado de rutas. El parche de aislamiento OAuth de tests/TestCase.php debe seguir presente; esta entrega no lo reemplaza.

No modifica .env. El antiguo FINANCIAL_HOLD_MAX_SECONDS ya no habilita nuevas retenciones ni funciona como alternativa a una política desactivada. Si una instalación tenía valores reales en ese mapa, deben darse de alta mediante la API con responsable y motivo antes de solicitar nuevas retenciones. No se importan silenciosamente políticas sin auditoría.

El vencimiento automático ya disponible sigue controlado por FINANCIAL_HOLD_SCHEDULE_EXPIRATION y por la infraestructura de scheduler. Crear políticas no habilita el scheduler. Comando manual: php artisan financial:expire-holds. En Windows de desarrollo se puede mantener php artisan schedule:work en otra terminal tras habilitar la opción y limpiar la caché de configuración. En servidor hay que ejecutar schedule:run cada minuto y configurar el almacenamiento de locks compartido si hay varias instancias.

## Validación

Se revisaron imports, cambios y manifiesto del ZIP. PHP y bases de datos no están disponibles en el entorno de preparación; el instalador hace lint y el verificador ejecuta las pruebas en el equipo del proyecto. No se afirma que las nuevas pruebas hayan pasado antes de esa ejecución.

Las pruebas cubren permisos, actor confiable, historial, duplicados, edición obsoleta, límites de duración, bloqueo por ausencia/desactivación, preservación de vencimientos, reintentos, cierres y rollback cuando falla el historial. Las duraciones TEST_CHECKOUT son fixtures exclusivos de testing. Los locks y versiones protegen concurrencia; las pruebas no equivalen a una carga simultánea multiproceso.
