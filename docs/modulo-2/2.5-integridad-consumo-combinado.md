# Integridad del consumo combinado de bonos

Base revisada: Equipo 2, commit 9b6bd2b. Complemento del refuerzo administrativo; no habilita emision ni cambia la autoridad E1.

## Problemas corregidos

consumeMultiple aceptaba importes sin comprobar su tipo: fracciones, booleanos o cadenas podian llegar a comparaciones, restas y persistencia. Ahora todo importe de un lote debe ser un entero PHP positivo en centavos. No se redondean ni convierten cadenas automaticamente. Los consumidores HTTP deben validar y convertir de forma explicita al preparar el comando de dominio; PurchasePaymentService ya construye enteros.

El metodo tambien indexaba los modelos por el UUID devuelto por SQL Server y los consultaba usando literalmente el ID de entrada. SQL Server uniqueidentifier puede devolver mayusculas mientras el consumidor envia minusculas. Ahora tanto el ID de entrada como la clave del modelo se normalizan a minusculas. Se rechaza un mismo UUID repetido aunque cambie su uso de mayusculas.

Antes de llamar a expireIfNeeded se valida el lote completo: lista consecutiva, dos o mas consumos, cada elemento como arreglo, UUID valido y monto entero positivo. Un segundo elemento malformado no provoca que se expire el primero durante una solicitud invalida. No se recortan espacios de identificadores ni se aceptan claves arbitrarias del arreglo como orden.

## Comportamiento conservado

Para lotes estructuralmente validos se mantienen las comprobaciones existentes de vigencia, beneficiario, moneda, combinabilidad, restricciones y saldo. No se modifica la politica de expiracion persistente existente, la transaccion de consumo ni el orden de bloqueo de bonos. No se acredita dinero en wallets. No hay nuevas migraciones, roles, APIs, UI, topes o fuentes de financiamiento.

Los UUID de SQL Server se comparan de manera canonica; esta correccion no declara compatibilidad probada con otro motor. El contrato de consumeMultiple ahora exige importes enteros reales; los strings numericos dejan de ser aceptados. La firma del metodo sigue igual.

## Validacion

Se incluyen pruebas unitarias sin Laravel ni base de datos para valores invalidos y duplicados, exigiendo que nunca se invoque expireIfNeeded. Tres pruebas funcionales verifican consumo real con mayusculas/minusculas, integridad de saldos y movimientos, rechazo previo a expiracion y duplicacion canonica.

El verificador conserva el preflight de Mongo campus_virtual_testing y SQL Server campus_digital_financial_testing antes de cargar TestCase. Esta suite elimina Mongo de pruebas; nunca apuntarla a datos locales o de integracion. No ejecuta migraciones ni llamadas a servidores E1/E4. Desactiva esas conexiones solo en su propio proceso y restaura las variables al finalizar.

No se ejecutaron PHP, PHPUnit/Pest ni SQL Server durante la preparacion. La integridad del ZIP se verifica localmente; ejecutar Verify-Changes.ps1 en Windows antes del commit. -FullFinancialSuite amplia a toda la regresion financiera.
