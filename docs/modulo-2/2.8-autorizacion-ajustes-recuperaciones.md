# 2.8 — Autorización de ajustes y recuperaciones

Base verificada: `98a4891`. Se extiende la segunda autorización a `ADJUSTMENT` y `WITHDRAWAL_RECOVERY`, reutilizando las políticas por asociación, moneda, versión y umbral.

## Alcance y semántica

- Ajuste: admite importes positivos y negativos. Se compara el valor absoluto contra el umbral inclusivo; el signo se conserva en el movimiento. No cambia la wallet ni corrige automáticamente diferencias de arqueo.
- Recuperación: requiere una devolución de retiro aprobada, sin recuperación previa, y un retiro originalmente liquidado en una caja de la misma asociación y moneda. El importe se obtiene de la devolución en el servidor; el cliente no puede introducirlo ni reemplazar el comprobante.
- Recuperar efectivo en caja y devolverlo a la wallet siguen siendo pasos distintos. La nueva autorización habilita solamente el registro físico; completar la devolución conserva las validaciones del 2.7.
- Sin política activa, o por debajo del umbral, no se exige supervisor. La interfaz prepara igualmente una solicitud para mostrar la regla aplicable y conservar una instantánea. Los clientes existentes pueden ejecutar directamente cuando no corresponde supervisor.
- Abrir/cerrar turnos, entradas/salidas físicas ordinarias y reversos no se modifican en esta entrega.

## Solicitud auditada

La nueva tabla `cash_administrative_requests` guarda UUID, turno receptor, tipo, importe firmado, moneda, devolución vinculada cuando corresponde, solicitante, motivo, clave/hash de solicitud, política capturada, estado, caducidad, supervisor, motivo de revisión, fechas, clave de ejecución y movimiento consumido. Las relaciones SQL impiden referencias inexistentes; los índices únicos filtrados impiden consumir una solicitud en varios movimientos.

La solicitud inicia en PENDING si exige supervisor o READY si puede ejecutarse sin él. Caduca según `financial.cash.confirmation_ttl_seconds`, validado entre 60 y 900 segundos. Un reintento exacto conserva la solicitud original y su caducidad; una clave con datos cambiados se rechaza. Cambiar/desactivar la política solo afecta solicitudes nuevas.

Un supervisor humano autorizado en la asociación puede aprobar o rechazar. No puede ser el solicitante, el operador responsable del turno ni, para una recuperación, el titular registrado de la wallet. No se infiere la identidad humana de una cuenta de servicio. Los tokens OAuth no pueden actuar como supervisores humanos.

Una aprobación no mueve efectivo. Solo el solicitante puede ejecutar con sus datos originales y su permiso de ajuste/recuperación vigente. Una aprobación no otorga otro permiso. Se comprueba de nuevo que el supervisor conserve `approval_review`. No se permiten nuevas ejecuciones de solicitudes rechazadas, canceladas, vencidas o consumidas. Las decisiones no se sobrescriben; sus reintentos exactos devuelven el estado original o consumido.

## Atomicidad y reintentos

La ejecución bloquea caja/turno y solicitud administrativa en un orden consistente; el servicio de recuperación conserva sus bloqueos sobre la transacción y devolución originales. Clave de ejecución, movimiento, comprobante, recuperación y consumo de autorización participan en la misma transacción SQL. Un fallo revierte el consumo y el efectivo; la aprobación ya registrada permanece para reintentar.

El hash del movimiento autorizado incorpora el UUID administrativo. Una autorización nueva no puede adherirse retroactivamente a un movimiento anterior. Un movimiento autorizado exige que sus reintentos mantengan el UUID y la clave originales. El reintento exacto de una ejecución consumida retorna el comprobante previo después del cierre, vencimiento o revocación; no produce efectivo adicional. Los reintentos de movimientos históricos sin autorización conservan su hash anterior incluso cuando se activa después una política.

El comprobante incorpora la solicitud, política y versión, necesidad de supervisor, supervisor, motivo y fecha. No se reconstruyen comprobantes históricos. No se introducen rutas para cambiar o borrar esta evidencia.

## API e interfaz

Pantallas existentes: Caja y `/finanzas/caja/autorizaciones`. Se agregan las dos operaciones al editor de reglas y una bandeja paginada de ajustes/recuperaciones pendientes.

Rutas API bajo `/api/v1/financial/cash/associations/{associationId}`:

| Ruta | Permiso OAuth y contrato |
| --- | --- |
| POST `/shifts/{shiftId}/administrative-requests` | `financial:cash:adjust` + `adjust`, o `financial:cash:recover` + `recover`, según tipo exacto |
| GET `/shifts/{shiftId}/administrative-requests/{administrativeId}` | Scope del tipo registrado + permiso del mismo tipo y solicitante propio |
| POST `/shifts/{shiftId}/administrative-requests/{administrativeId}/cancel` | Scope del tipo registrado + permiso del mismo tipo y solicitante propio |
| GET `/administrative-approval-requests` | `financial:cash:approval:read` + `approval_read` |

Ajustes y recuperaciones externos conservan sus rutas de ejecución, añadiendo `administrative_request_id` cuando existe una solicitud. Si falta y la política actual exige supervisor, responden 409 sin registrar efectivo. Los scopes se comprueban independientemente del permiso de asociación; `financial:write`, `operate` o un UUID conocido no los reemplazan.

La revisión humana se realiza mediante sesión/CSRF: POST `/finanzas/caja/asociaciones/{associationId}/administrative-approval-requests/{administrativeId}/{approve|reject}` con `approval_review`. El actor se obtiene del servidor y se ignoran actores enviados en el cuerpo. Las consultas se limitan a asociación, turno y solicitante según su función. La bandeja no mezcla los UUID administrativos con las confirmaciones de titular.

Los servicios internos `addMovement` y `recover` conservan sus firmas compatibles para código confiable e integración. Los controladores externos invocan siempre la barrera de autorización. Nuevas rutas no deben exponer los servicios internos como alternativa para saltar políticas.
