# Panel de emisión BECA por Consejo

La pantalla de administración de bonos muestra el panel de Comunidad cuando la integración BECA está habilitada, la sesión de E1 está vigente y existe una designación efectiva de emisor para un Consejo vinculado a un presupuesto en la configuración de Finanzas. La comprobación usa los servicios de designación, sesión y vigencia de E1.

El formulario confirma el TOTP mediante la ruta existente de E1. El código se borra después de cada intento. La revisión y emisión mantienen la autorización completa del backend sobre Consejo, presupuesto, Tesorería y emisor. Una denegación descarta la revisión y pide confirmar nuevamente el segundo factor.

Si se pierde la respuesta de emisión, la pantalla descarta la confirmación anterior y permite consultar la misma referencia para recuperar el comprobante. La API conserva su control de idempotencia.

Las pruebas cubren la visibilidad sin autoridad administrativa genérica, revocación de la designación, ausencia de sesión, configuración inválida, segundo factor rechazado y recuperación de la respuesta de emisión. Las concesiones productivas y la activación del entorno siguen los controles de E1 y Finanzas.

## Validación del transporte

En una red Docker aislada, con MongoDB y SQL Server desechables, se verificaron 13 comprobaciones sobre una beca sintética. El controlador de Finanzas usó HTTP real y OAuth para consultar el dictamen de Comunidad y la autorización de Identidad. La emisión comprometió 3,000 centavos del presupuesto y se conservó un solo bono al repetir la solicitud. El worker de Comunidad recuperó el comprobante de Finanzas y marcó la asignación como entregada incluso después de revocar al emisor. También se verificaron el rechazo sin token, el scope incorrecto y la falta o revocación de la designación.

La prueba inicializó un presupuesto sintético y una sesión de prueba con TOTP. Verificó los controladores, servicios, persistencia y transporte entre módulos. El recorrido del operador en un navegador y la configuración del entorno de presentación requieren su propia comprobación.

## Preparación del piloto

E1 registra tres clientes de servicio de alcance mínimo. Finanzas consulta E1 con `identity:financial-authorization:check` y Comunidad con `community:beca-award:read`. El cliente de Comunidad consulta el comprobante en Finanzas con `financial:beca-issuance:read`. En testing o local, el cliente de autorización financiera admite HTTP por loopback. Para orígenes de red se requiere HTTPS.

E2 configura la convocatoria, Consejo, UUID del presupuesto y negocio mediante `FINANCIAL_COMMUNITY_BECA_BUDGETS_JSON`. E6 conserva el dictamen de Presidencia y el aval de Tesorería. El piloto requiere `COMMUNITY_BECA_FINANCE_ENABLED` y `FINANCIAL_IDENTITY_AUTHORIZATION_ENABLED` en el entorno autorizado. Las designaciones creadas por el piloto corresponden al laboratorio.
