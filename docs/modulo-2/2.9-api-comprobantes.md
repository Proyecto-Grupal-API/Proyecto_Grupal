# 2.9 — API de consulta personal de comprobantes

## Rutas y respuestas

- GET `/api/v1/financial/receipts?page=1&per_page=20`: listado paginado, `data` con `id`, `source`, `created_at`; `meta` con total, current_page, per_page, last_page, api_version y correlation_id.
- GET `/api/v1/financial/receipts/transaction/{UUID}`: participación de la wallet del usuario en una transacción.
- GET `/api/v1/financial/receipts/purchase/{UUID}`: pago de compra, incluido pago íntegro con bonos.

Usar el `source` retornado por el listado en minúsculas para construir el detalle. Una transacción PURCHASE vinculada a un pago puede devolver el comprobante de ese pago, cuyo id y source son los del pago. Estos IDs son referencias a registros existentes, no folios nuevos de emisión.

Las rutas son solo lectura. No requieren Idempotency-Key, no crean wallet, comprobante, transacción ni asignación de permiso. Reutilizan PersonalReceiptQueryService, también utilizado por la interfaz del commit f0d9441. La respuesta de detalle filtra movimientos ajenos y razones/metadatos administrativos. Un folio de caja registrado se consulta sin reemitirlo.

## Dos autorizaciones independientes

Cabeceras necesarias:

```
Authorization: Bearer TOKEN_DE_SERVICIO
X-User-Authorization: PRUEBA_FIRMADA_O_REFERENCIA_OPACA_VALIDADA_POR_IDENTIDAD
X-Correlation-Id: UUID_OPCIONAL
```

El token debe incluir `financial:receipt:read`. `financial:read` no sustituye ese scope. El cliente debe tener dicho scope en su catálogo de ServiceClient; solicitarlo al endpoint OAuth no lo concede si no está autorizado previamente.

ReceiptDelegationProvider resuelve el usuario. Su implementación confiable DEBE verificar emisor, firma, audiencia, expiración, consentimiento de consulta, vínculo con cliente autenticado, acción y digest, cuenta/sesión vigente y revocación en cada consulta. El token de servicio identifica a una aplicación y no al estudiante. No convertir `sub` del token en ID del usuario, ni aceptar user_id/wallet_id del solicitante. No reutilizar un permiso de transferencia como permiso de comprobantes.

Acciones: `receipt.list` y `receipt.read`.
Digest SHA-256 sobre JSON UTF-8 con claves superiores `method`, `path`, `query`; method en mayúsculas, path con `/` inicial sin query, query ordenada recursivamente por claves para objetos (listas conservan orden). JSON_UNESCAPED_SLASHES y JSON_UNESCAPED_UNICODE. La prueba vincula exactamente el hash de ResolveReceiptDelegation::digest(). page/per_page permanecen como strings del query HTTP. Otro cliente, ruta, acción o página requiere prueba correspondiente. Se permite repetición de la misma consulta mientras la prueba siga vigente; no se acepta una revocación aunque un comprobante anterior fuera accesible.

GET no admite cuerpo ni parámetros distintos a page/per_page. Paginación: page >=1 y <=1000000; per_page entre1 y50. La protección de frecuencia es de30 solicitudes/minuto por identidad de cliente HTTP/IP que usa el middleware Laravel, compartida entre estas rutas; no es un límite monetario y no garantiza una cuota independiente por cliente OAuth.

## Proveedor provisional y reversibilidad

`config/financial_receipts.php` selecciona delegation_provider. Por defecto usa PendingReceiptDelegationProvider: devuelve503 y NO autoriza a ningún usuario. La API queda implementada, pero su uso real depende de conectar el contrato de Identidad; las pruebas utilizan un doble acotado a pruebas, no un proveedor permisivo de desarrollo.

Para integrar Identidad se implementa únicamente ReceiptDelegationProvider y se registra su clase en la configuración. No hay fallback automático a otro proveedor cuando la validación falla. No se modifican los contratos de transferencias ni los roles generales. Consulta administrativa ajena y su contexto/capacidad quedan fuera de estas rutas personales.

401: token/proof ausente o inválido, prueba expirada o revocada.403: scope o consentimiento insuficiente.404: comprobante inexistente o ajeno.409: operación o desglose sin evidencia coherente.422: paginación/cuerpo/selección de identidad inválidos.429: frecuencia excedida.503: contrato pendiente, dependencia caída o respuesta inválida. Las fallas del proveedor se reportan en el servidor; nunca se incluyen pruebas crudas ni detalles técnicos privados en la respuesta. El proveedor debe redactar excepciones para no incluir pruebas/secretos en su mensaje.

No se afirma que todos los errores de validación devuelvan el mismo envelope: errores usan el manejo HTTP estándar de Laravel y las consultas correctas retornan data/meta. La correlación se usa en respuestas correctas y cabecera de respuesta mediante el middleware financiero existente.
