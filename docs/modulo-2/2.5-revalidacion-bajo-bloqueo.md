# R2 — Revalidación de autoridad bajo bloqueo

Base 83e9a82. Agrega controles actuales, sin cambiar permisos, hashes de idempotencia, orden de bloqueos o efectos contables.

InstitutionalBudgetService vuelve a exigir budget.adjust/suspend/resume después de bloquear el presupuesto; los reintentos exitosos también exigen la decisión correspondiente después del bloqueo. En aprobación nueva, sin presupuesto existente que bloquear, repite budget.approve dentro de la transacción después de adquirir el lock de solicitud; el replay revalida después de bloquear el presupuesto creado y conserva el ámbito global null de aprobación.

InstitutionalBecaIssuanceService vuelve a comprobar budget.commit y bonus.issue después de obtener el bloqueo presupuestario, antes de emitir o resolver replay. Conserva la comprobación existente del emisor. InstitutionalBecaReleaseService vuelve a comprobar budget.release/expire y, para cancelación, bonus.cancel después de bloquear presupuesto y bono; también aplica a replay.

Una autorización retirada mientras se esperaba el bloqueo ya no puede ser utilizada como la decisión actual en esos puntos. Fallos o denegaciones no devuelven replay exitoso ni persisten cambios parciales. No se promete eliminar toda ventana temporal: una autorización externa puede cambiar después de la última comprobación. La validez transaccional entre bases distintas requiere un contrato adicional; no se inventa una reserva de autoridad.

Los contratos E2 consultados siguen siendo los existentes y sus proveedores Pending continúan denegando. No se habilita administración ni se modifica la integración HTTP E1. Los adaptadores de autoridad usados en esta sección crítica deben ser apropiados para ella; esta entrega no incorpora clientes HTTP ni llamadas externas nuevas.

Las 19 pruebas nuevas simulan decisiones que permiten la entrada y deniegan la revalidación, incluidas repeticiones y fallo de dependencia. Comprueban la mayor profundidad transaccional del segundo control y el estado financiero sin cambios. No son una prueba de espera SQL con conexiones independientes ni de revocación real de E1; esa validación integrada sigue pendiente.

Sin migraciones nuevas, rutas, cambios Vue ni .env. Verify-Changes.ps1 usa exclusivamente bases de testing, integraciones reales y scheduler desactivados, prepara solamente migraciones institucionales existentes y restaura las variables del proceso. No se necesita npm build. R1 se conserva; R3 del historial de liquidación sigue pendiente.
