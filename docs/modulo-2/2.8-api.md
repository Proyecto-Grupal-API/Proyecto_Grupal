# 2.8 — API de caja con autorización por asociación

Base: e8e1152. Este bloque publica diez rutas sobre la base de caja verificada. Conserva los servicios, migraciones e interfaces anteriores. No necesita nuevas migraciones ni modifica .env.

## Rutas y permisos

Prefijo: /api/v1/financial/cash/associations/{associationId}

| Método | Ruta | Scope OAuth | Acción del proveedor |
|---|---|---|---|
| GET | /registers | financial:cash:read | read |
| GET | /registers/{registerId}/shifts | financial:cash:read | read |
| GET | /shifts/{shiftId} | financial:cash:read | read |
| GET | /shifts/{shiftId}/movements | financial:cash:read | read |
| POST | /registers/{registerId}/shifts | financial:cash:operate | operate |
| POST | /shifts/{shiftId}/movements | financial:cash:operate | operate |
| POST | /shifts/{shiftId}/topups | financial:cash:operate | operate |
| POST | /shifts/{shiftId}/withdrawals | financial:cash:operate | operate |
| POST | /shifts/{shiftId}/adjustments | financial:cash:adjust | adjust |
| POST | /shifts/{shiftId}/close | financial:cash:close | close |

Todas las rutas requieren token válido y autorización independiente de asociación. financial:read, financial:write y los permisos administrativos de 2.7/2.10 no habilitan caja.

CashAuthorizationProvider::allows(actorId, associationId, action) es el punto de integración con los contratos confiables de Módulos 1 y 6. PendingCashAuthorizationProvider devuelve false. Hasta sustituir su binding en AppServiceProvider con un adaptador real, la API responde 403 incluso si el token tiene scope. Esto es intencional: no se infieren permisos de roles autoasignados ni se concede acceso global. Las pruebas usan un proveedor temporal que compara exactamente actor, asociación y acción; no se instala un proveedor permisivo en producción.

Actor: service:<sub del token OAuth validado>. No se acepta actor_id, agent_id ni closed_by del payload como identidad. La API identifica al cliente de servicio; no afirma conocer a un cajero humano delegado. Para hacerlo se necesita un contrato confiable de delegación. El turno se abre para ese actor; movimientos ordinarios, recargas y retiros exigen que coincida con su operador. adjust y close pueden autorizar a un supervisor de la misma asociación de manera independiente.

El proveedor debe consultar asignaciones vigentes y estado de asociación/servicio, denegar si no hay una concesión explícita y fallar sin ejecutar la operación ante una dependencia no disponible. Cambiar solamente este adaptador mantiene rutas, controlador y futura interfaz. No reutiliza walletId como associationId.

## Solicitudes

Cada POST requiere Idempotency-Key no vacío, máximo 255 caracteres. Apertura: opening_amount_cents >= 0. Movimiento ordinario: type CASH_IN/CASH_OUT, amount_cents >= 1, reason obligatorio máximo 1000. Ajuste: amount_cents entero distinto de cero, reason; no recibe type. Recarga/retiro: wallet_id UUID, amount_cents >= 1, reason. Cierre: counted_amount_cents >= 0, reason.

No se fabrican TOPUP/WITHDRAWAL mediante movimientos manuales. Las liquidaciones delegan en CashSettlementService: operación financiera, ledger, saldo y movimiento físico se confirman o revierten juntos. No se agrega una transacción HTTP exterior que revierta la evidencia de límites bloqueados.

Cada asociación filtra sus propios registros y turnos antes de operar. Un UUID de otra asociación devuelve 404 en una asociación autorizada; una asociación sin concesión devuelve 403 antes de consultar sus registros.

GET de turnos devuelve esperado calculado si está abierto y snapshot inmutable si está cerrado. Listados aceptan page y per_page (1–100, inicial 25). Orden descendente por ID; meta.pagination conserva current_page/per_page/total/last_page. UUID públicos se serializan en minúsculas para evitar diferencias de SQL Server.

Respuestas de POST exitoso: 200 tanto en primera ejecución como reintento. 401 token ausente/inválido; 403 scope o asociación/operador insuficiente; 404 registro inexistente o fuera de asociación; 422 validación/clave ausente; 409 conflicto de estado, fondos o clave reutilizada. Bloqueo de límites conserva error.code FINANCIAL_LIMIT_EXCEEDED, evaluación y referencia de alerta. Una colisión simultánea de restricción única devuelve 409 y permite reintentar con la misma clave.

## Alcance pendiente

Este bloque no publica alta/edición de cajas: createRegister sigue siendo una operación interna confiable, sin ofrecer una escritura HTTP no idempotente. Faltan administración de cajas con historial, adaptador real de permisos, interfaz 2.8, comprobantes/folios y recuperación/devolución física de efectivo. Tampoco activa permanentemente conciliación de caja. No se declara terminado todo el 2.8.
