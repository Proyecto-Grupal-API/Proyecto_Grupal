# Refuerzo de emisión administrativa de bonos

Base revisada: Módulo 2 `7460d47`. Este cambio no conecta el merge completo ni modifica E1.

## Cambios

- Las escrituras web de emisión y cancelación exigen una cuenta actual activa y verificada y una sesión registrada, existente, no revocada y perteneciente al usuario autenticado. El middleware se ejecuta antes de session.active y device.track y solo actúa en esas dos rutas. Así no se crea una sesión de reemplazo dentro de una escritura rechazada. Una sesión ausente requiere volver a iniciar sesión.
- La emisión administrativa impide que el emisor sea su beneficiario, comparando el ID canónico sin distinguir mayúsculas. La regla también protege llamadas directas a BonusAdministrationService. No se anuncia protección nueva de autoasignación para todos los consumidores internos de BonusService.
- Controlador y servicio comparten las reglas de entrada. Se rechazan contextos administrativos no admitidos, importes fraccionarios, IDs y fechas inválidas. Se validan motivo, llave, vigencia, beneficiario y restricciones antes de consultar el permiso específico de emisión. El permiso web genérico se comprueba primero para evitar revelar beneficiarios a actores sin acceso.
- Beneficiario, vigencia y restricciones se vuelven a validar al crear una operación dentro de la transacción. No existe transacción distribuida entre Mongo y SQL Server: una revocación concurrente posterior a una lectura sigue siendo una limitación a resolver mediante el contrato aprobado.
- BonusService comprueba emisor obligatorio y orden de fechas antes del proveedor de autorización. Se conserva su firma y la política de tipos de emisor ya existente para no romper los consumidores actuales.
- Se preservan idempotencia, transacción SQL de bono/restricciones/auditoría y permisos independientes de consulta y cancelación. No se añade ningún permiso ni rol.

## Límites deliberados

La administración sigue bloqueada por PendingFinancialWebAuthorizer. Un authorized=true de E1 solo prueba capacidad técnica para issue; no habilita view, view.all, cancel ni cancel.all. No se altera .env ni se desactiva la conexión HTTP configurada por el usuario. El verificador desactiva temporalmente integraciones dentro de su proceso de pruebas y restaura esas variables al terminar.

Siguen pendientes autoridad otorgante E1, fuente y aprobación de financiamiento, topes institucionales, eventual doble aprobación y la política de reautenticación/segundo factor reciente. Una sesión registrada no constituye evidencia de segundo factor reciente. La emisión web permanece cerrada; este paquete no la declara lista para uso real.

Se mantienen las lecturas locales existentes de User y UserSession. No se presenta este cambio como independencia completa de Identidad: sustituirlas por un contrato aprobado es trabajo posterior y debe coordinarse con E1.

## Verificación

No se ejecutó PHP, Pest ni SQL Server en el entorno de preparación. Ejecutar Verify-Changes.ps1 en Windows. El script comprueba los destinos de bases de pruebas antes de cargar TestCase, porque ese TestCase elimina el contenido de Mongo de pruebas. Nunca ejecutar estas suites apuntando a campus_virtual o campus_virtual_e1_integracion.

Se amplía BonusAdministrationWebTest con sesión ausente, inválida, ajena y revocada, cuenta deshabilitada, autoasignación, entrada rechazada antes de consultar al emisor, llamada administrativa directa y fechas de dominio. Los casos positivos existentes usan sesiones registradas reales del fixture; no se desactiva el nuevo middleware. Los proveedores permisivos solo existen en los tests.

El filtro focal ejecuta el consumidor E1, administración, dominio de bonos, consulta personal, pagos y devoluciones. -FullFinancialSuite ejecuta toda la suite financiera. No hay migraciones, cambios Vue ni necesidad de npm build.
