# BECA: pruebas con procesos SQL independientes

Base revisada: `8687bd5`. Esta entrega agrega exclusivamente herramientas bajo `tests/Concurrency/InstitutionalBeca`; no cambia servicios, permisos, rutas, migraciones ni Vue.

## Alcance y resultados exigidos

| Caso | Operaciones simultáneas | Resultado exigido |
|---|---|---|
| Compras competidoras | Dos compras de 2,000 centavos sobre un bono de 3,000 | Una compra y un conflicto; consumido 2,000, comprometido 1,000; un evento |
| Misma compra | Dos procesos, mismo pedido y misma llave | Una sola compra; conflicto transitorio o replay permitido; el reintento devuelve la compra original |
| Misma devolución | Dos procesos completan la devolución aprobada de 400 sobre una compra de 1,000 | Una transacción de devolución; consumido 600 y comprometido 2,400; dos eventos totales |
| Cierre del ciclo anterior | Registrar liquidación de 600, repetirla y cancelar el remanente | Una liquidación; devuelto 400, liquidado 600, pendiente 0; compromiso 0 y conciliación consistente |

La última fila es secuencial. Las tres primeras usan procesos PHP reales mediante Symfony Process, cada uno con conexión SQL y PID distintos. No se usa `Tests\TestCase`, ni transacción exterior compartida ni solicitudes HTTP fingidas como sustituto de concurrencia SQL.

El padre mantiene un bloqueo SQL real sobre el presupuesto. Los hijos publican su PID/`@@SPID`, esperan la barrera de inicio y anuncian inmediatamente antes de enviar la consulta `UPDLOCK`. El padre exige que ambos procesos hayan alcanzado ese punto; para llaves idénticas admite que uno ya haya recibido conflicto del candado de idempotencia. Antes de liberar el bloqueo, ninguna operación puede haber terminado con éxito. Después se verifican resultados, reintentos y evidencia persistida. La señal previa a la consulta no mide el tiempo de espera dentro del servidor; no requiere permisos para consultar las DMV de otras sesiones.

Solo se admiten los conflictos de dominio 409 previstos por cada caso. Deadlocks SQL 1205, timeout SQL 1222, fallos de proceso o infraestructura hacen fallar la ejecución. No hay reintentos automáticos que oculten esos errores.

## Aislamiento

Se exige `APP_ENV=testing`, `BECA_SQL_CONCURRENCY=1`, conexión predeterminada MongoDB y las bases exactas:

- SQL Server: `campus_digital_financial_testing`, comprobada además con `DB_NAME()`.
- MongoDB: `campus_virtual_testing`, comprobada en la conexión efectiva.

No ejecutar junto con otras suites, `migrate:fresh`, workers o schedulers que usen estas mismas bases de testing. El candado `sp_getapplock` excluye otra instancia de este ejecutor, pero otras suites existentes no respetan ese candado.

Se necesitan los esquemas financieros ya migrados en testing, PHP CLI con SQLSRV/MongoDB y las dependencias de desarrollo de Composer. No se requiere arrancar E1 ni E4. El servidor habitual de desarrollo puede seguir abierto si usa otras bases.

Los datos SQL se confirman para ser visibles entre conexiones. Cada ejecución crea usuarios, wallet de comprador vacía, presupuesto y bono sintéticos con identificadores propios. Las autorizaciones son implementaciones exclusivas de este proceso de testing y limitadas a sus sujetos; no se conceden roles reales ni se cambia un binding de producción. La liquidación usa evidencia sintética: no verifica ni envía pagos bancarios.

La limpieza usa identificadores de los recursos creados y orden de claves foráneas; no usa `drop`, `truncate`, borrados globales ni elimina registros de desarrollo. También se intenta al fallar. Un cierre forzado del proceso padre puede impedirla; conservar el identificador de ejecución y el informe antes de investigar. No ejecutar un borrado masivo como recuperación.

## Ejecución

Aplicar el paquete y ejecutar su `Verify-Changes.ps1 -ProjectPath C:\Proyectos\Campus-Digital`. El script establece y restaura variables exclusivamente del proceso, desactiva llamadas reales y ejecuta `php tests/Concurrency/InstitutionalBeca/run.php`. No modifica `.env`, no migra y no compila Vue.

La salida debe terminar con tres carreras aprobadas, cierre de ciclo aprobado y limpieza `OWNED_FIXTURES_REMOVED`. El informe JSON se guarda en `storage/logs/beca-concurrency-<run_id>.json`; incluye PID, SPID, duración y resultado de cada proceso. Las señales de sincronización quedan en `storage/framework/testing/beca-concurrency-<run_id>*` para diagnóstico.

El paquete se revisó estáticamente al prepararlo. Su resultado en SQL Server solo se puede declarar después de ejecutar el verificador en ese entorno. Un resultado positivo no acredita autoridad institucional productiva, integración real con E1/E3/E4, pagos bancarios, carreras entre todos los servicios ni carga sostenida. Los bloqueos productivos existentes permanecen vigentes.
