# Exposición y respaldo financiero de bonos

Base de Módulo 2: `3973bd0`. El diagnóstico es operativo y de solo lectura; el diseño de respaldo de la segunda parte es una propuesta funcional pendiente de aprobación, no una política activada.

## Diagnóstico disponible

```powershell
php artisan financial:bonus-exposure --type=BECA --currency=MXN
```

Sin filtros, agrupa todos los registros por tipo, moneda, estado almacenado y clasificación temporal. No suma monedas diferentes ni mezcla dinero de wallets con saldo de bonos. Las cantidades se expresan como strings de centavos enteros, conservando exactitud incluso cuando la suma excede el entero PHP. No son valores en pesos ni floats. `bonus_count` también se devuelve como string entero.

| Clasificación | Significado |
| --- | --- |
| AVAILABLE | Registro abierto, saldo positivo y vigencia actual. Describe saldo potencialmente utilizable, no confirma elegibilidad del beneficiario, restricciones de una compra ni financiamiento. |
| SCHEDULED | Registro abierto con saldo y comienzo de vigencia futuro. |
| EXPIRED_UNPROCESSED | Saldo positivo vencido que todavía está registrado en un estado abierto. La consulta no ejecuta su expiración. |
| TERMINAL | Agotado, cancelado o expirado sin saldo pendiente. |
| TERMINAL_WITH_BALANCE | Estado terminal con saldo positivo; requiere investigación. |
| OPEN_WITHOUT_BALANCE | Estado abierto con saldo cero; requiere revisión de estado. |
| INVALID_RECORD | Monto o saldo fuera de rango, fechas incoherentes, estado o tipo desconocido, o moneda con longitud inválida. No se corrige el registro. |

`funding_evidence=NOT_RECORDED_IN_CURRENT_SCHEMA` indica que el esquema actual no vincula los bonos con una fuente aprobada. No prueba que no exista financiamiento fuera del sistema ni acredita que esté disponible. `funding_certified=false` siempre; ni AVAILABLE ni un ledger conciliado certifican respaldo.

La consulta usa una sola sentencia SQL de agregación para reducir lecturas separadas. `observed_at` es el momento UTC de evaluación temporal. No activa aislamiento snapshot ni adquiere reservas: con concurrencia se rige por el aislamiento configurado en SQL Server. El resultado es diagnóstico, no una certificación ni una base para autorizar débitos. No admite fechas históricas: opera sobre saldos almacenados actuales, sin reconstruir el saldo de otro día.

No accede a Mongo ni E1, no expone identidades de beneficiarios/emisores y no llama a proveedores de permisos o HTTP. El comando exige acceso a la consola del servidor; no se publica en API ni interfaz de usuario. No debe exponerse como endpoint sin autorización administrativa independiente.

No escribe bonos, movimientos, wallets, auditorías, catálogos ni permisos. La conciliación existente continúa siendo la herramienta para comparar saldos y ledger; este diagnóstico no sustituye sus comprobaciones ni las duplica como una nueva certificación.

## Diseño propuesto del respaldo

El permiso de emisión de E1 no determina disponibilidad de presupuesto ni permite elegir cualquier wallet. E2 es responsable de llevar la relación entre fuente aprobada, presupuesto comprometido y bono. Hay dos conceptos que requieren acuerdo antes de integrar efectos monetarios: presupuesto contable aprobado y efectivo realmente custodiado. No se tratarán como equivalentes.

Propuesta para la primera entrega BECA global:

1. Registrar una fuente con referencia estable, moneda, responsable, evidencia de aprobación y política vigente. Alta y cambios exigen una autoridad financiera aprobada; no habrá autoasignación ni un administrador implícito.
2. Recibir una asignación de presupuesto explícita y trazable, sin convertirla en una recarga ni inventar fondos de wallet. Si la fuente exige efectivo custodiado, deberá acreditarse con evidencia y mecanismo contable acordados.
3. Reservar el importe autorizado al emitir el bono y registrar bono, vínculo de fuente, compromiso y auditoría en una misma transacción SQL. Si falla cualquier parte, no debe existir emisión parcial.
4. El consumo debe trasladar importe comprometido a consumido, sin crear dinero en la wallet del beneficiario. La liquidación al negocio es un proceso separado que todavía requiere contrato y contraparte financiera.
5. Cancelación o expiración liberan solo la parte no consumida y una sola vez. Un reintento no restituye dos veces el presupuesto.
6. Un reembolso debe mantener el vínculo con la fuente original y distinguir devolución al bono de devolución al presupuesto. No reactivar automáticamente un bono vencido; la regla de recuperación requiere aprobación.
7. Los bonos históricos no se vinculan automáticamente a una fuente nueva. Debe existir revisión y evidencia; conservar su estado como respaldo no registrado hasta que se acredite.

## Pruebas y límites de entrega

Se incluyen cinco pruebas funcionales: clasificación por vigencia; separación de monedas y anomalías; sumas exactas superiores a PHP_INT_MAX; filtros rechazados antes de SQL y salida CLI sin identidades; resultado vacío sin creación de recursos. Los fixtures de datos y el proveedor permisivo de emisión son exclusivos de testing y se revierten dentro de transacciones SQL.

No se ejecutaron PHP, Pest ni SQL Server durante la preparación. El verificador debe ejecutarse en Windows contra las bases aisladas. Antes de cargar TestCase comprueba Mongo `campus_virtual_testing` y SQL Server `campus_digital_financial_testing`. Nunca ejecutar esa suite contra datos de desarrollo o la base E1 de integración.
