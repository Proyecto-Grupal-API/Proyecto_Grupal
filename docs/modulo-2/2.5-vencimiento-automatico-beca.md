# 2.5 Vencimiento programable de BECA institucional

Base: 4dc4ca0. Reutiliza InstitutionalBecaReleaseService::expire; no cambia su autorización, auditoría, transacción ni validaciones de integridad. No hay migraciones nuevas ni cambios Vue.

## Resultado contable

Una BECA ACTIVO/PENDIENTE con expires_at <= instante del barrido puede vencer. Se libera exclusivamente remaining_amount_cents: baja committed_amount_cents, se conserva consumed_amount_cents, se incrementa la versión y se registra EXPIRE_BECA + movimiento EXPIRACION / BUDGET_RELEASE. Ejemplo: bono de $30 con $10 consumidos libera $20; los $10 de obligación al negocio se conservan.

No crea dinero, no acredita wallets, no liquida deudas, no entrega eventos a E4 y no convierte bonos históricos sin respaldo en institucionales. No reactiva bonos ni habilita devoluciones después del vencimiento. El flujo de devolución de bonos terminales sigue requiriendo su tratamiento explícito separado.

## Comando

Desde la raíz del proyecto, con una identidad auditada real de 24 caracteres hexadecimales configurada:

```powershell
php artisan financial:expire-institutional-becas
```

Sin --confirm es únicamente una consulta de candidatos. PREVIEW no certifica integridad ni permisos de ejecución. La CLI es operativa y exige control de acceso al servidor.

```powershell
php artisan financial:expire-institutional-becas --confirm --all
```

--actor permite indicar explícitamente la identidad auditada en vez de la configuración. No es evidencia de consentimiento humano ni una concesión de permisos. Cada operación exige InstitutionalBudgetAuthorization::allows(actor, 'budget.expire', budget_id). El proveedor Pending actual deniega: ni el comando ni el scheduler otorgan autoridad.

--limit=100 limita cada lote (1..500); --after=0 es el cursor exclusivo numérico. --all recorre todos los lotes hasta el máximo ID inicial, con instante de corte fijo. Produce una línea JSON por lote y mantiene memoria acotada. Sin --all retorna has_more/next_cursor para una inspección limitada. Un barrido nuevo toma un corte nuevo.

EXPIRED indica liberación confirmada. DENIED requiere autoridad aprobada; REVIEW_REQUIRED puede indicar carrera de versión, bloqueo ocupado, vínculo ausente o evidencia inconsistente; UNAVAILABLE indica fallo de dependencia/persistencia. Estos estados devuelven código de salida no cero. No se imprimen mensajes SQL ni excepciones privadas. Se procesan los siguientes candidatos aunque alguno falle. Los errores no desaparecen silenciosamente ni reparan datos automáticamente; deben revisarse con las consultas institucionales existentes.

## Consistencia y recuperación

Cada bono ejecuta su propia transacción; el barrido no envuelve el lote en otra transacción. Se conservan el bloqueo SQL por llave, el orden presupuesto->bono, la versión optimista y las comprobaciones antes/después. La llave estable por bono es institutional-beca-expire:<UUID canónico>. Si otro proceso gana una carrera, se devuelve revisión y el siguiente barrido reevalúa el estado. Si el proceso cae después del commit, el bono ya terminal no se selecciona otra vez. Si falla el ledger/auditoría, la liberación se revierte y permite reintento.

Se incluyen candidatos con marca institucional o evidencia en compromisos/obligaciones; perder la marca no habilita el camino legado. Los bonos cancelados, agotados o ya expirados quedan fuera del barrido; las anomalías de esos estados se investigan mediante conciliación, no por reparación automática.

## Programación

Configuración explícita, solo cuando exista una identidad autorizada y un procedimiento operativo aprobado:

```dotenv
FINANCIAL_INSTITUTIONAL_BECA_EXPIRATION_ENABLED=true
FINANCIAL_INSTITUTIONAL_BECA_EXPIRATION_ACTOR=<identidad auditada autorizada>
```

El instalador NO cambia .env y la tarea está deshabilitada por defecto. Un actor inválido impide registrarla. La tarea se registra cada minuto con --confirm --all, y withoutOverlapping usa el mutex del scheduler configurado por el proyecto. El lock SQL del dominio y la versión siguen protegiendo operaciones desde procesos o servidores independientes; no se presupone un cache compartido.

Se necesita un scheduler de Laravel activo; el servidor HTTP por sí solo no ejecuta tareas programadas. En desarrollo, después de completar autorización y configuración, se utiliza una terminal aparte con php artisan schedule:work. En producción el despliegue debe invocar schedule:run cada minuto. La precisión depende de disponibilidad del proceso e infraestructura, no del reloj del navegador. No se registra ejecución durante mantenimiento por defecto.

Referencias: https://laravel.com/docs/13.x/scheduling (scheduler y withoutOverlapping).
