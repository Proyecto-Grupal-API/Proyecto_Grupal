# 2.8 — Comprobantes de movimientos de caja

Base: 094deb2. La administración anterior está verificada con 329 pruebas financieras / 2504 aserciones. Este bloque agrega comprobantes operativos para los movimientos nuevos de caja, consulta API/web e impresión desde el navegador. Requiere una nueva migración en desarrollo y pruebas; no modifica .env.

## Emisión atómica

Nueva tabla cash_receipts: UUID único, un comprobante por cash_movement_id (FK y restricción única), folio único de máximo 50 caracteres, snapshot JSON e issued_at. No hay borrado en cascada de comprobantes. No se añade contador secuencial compartido: el folio usa CAJ-AAAAMMDD-UUID sin guiones (45 caracteres) y SQL Server impone su unicidad.

CashReceiptService emite dentro de la transacción SQL existente de CashShiftService::addMovement o CashSettlementService. Se registra para CASH_IN, CASH_OUT, ADJUSTMENT, TOPUP y WITHDRAWAL nuevos. En recarga/retiro verifica que exista la transacción financiera completada y copia el mismo folio a TopUp/Withdrawal.

Movimiento, comprobante, operación financiera, ledger, saldo y folio se confirman o revierten juntos. Si falla emitir el comprobante o guardar el folio, el dinero no queda confirmado parcialmente. El flujo preventivo de límites y evidencia bloqueada conserva su manejo anterior. No se añade una transacción externa alrededor del controlador.

Reintento: recupera movimiento/operación existente con su comprobante y folio originales. El UUID y la FK únicos previenen duplicados; el hash de solicitud existente rechaza cambios de importe/actor/etc. Consultar e imprimir no emiten nada ni ejecutan movimientos. El servicio no tiene endpoint HTTP de emisión ni actualización.

## Snapshot y datos

Snapshot de versión de formato 1: identificador y folio del comprobante, fecha, asociación, caja (UUID/nombre/versión), turno, movimiento, tipo, importe en centavos, moneda, actor, motivo, wallet opcional, referencia de operación y UUID de transacción financiera si aplica. No consulta perfiles externos ni agrega datos personales del beneficiario.

Los datos mostrados provienen del snapshot guardado, no del nombre actual de caja ni de una reconstrucción del saldo. Renombrar una caja, cerrar un turno o reimprimir no cambia el comprobante original. El responsable es service:<sub OAuth> o user:<ID de sesión>, según el origen autenticado ya establecido; no se aceptan datos del payload para suplantarlo.

Las recargas/retiros comunes fuera de CashSettlementService conservan su lógica anterior y no reciben comprobantes de caja por este bloque. Tampoco se emiten comprobantes para apertura/cierre de turno: estos mantienen su resumen/arqueo ya implementado; aquí se documentan movimientos de efectivo. No se implementa factura fiscal ni firma externa.

## Movimientos históricos

No se generan comprobantes retroactivos ni se rellenan folios antiguos: sus datos originales no están disponibles como snapshot. Los movimientos anteriores muestran Sin comprobante. Reintentar una operación histórica sigue devolviendo la operación original, sin fabricar una fecha o nombre de caja histórico con datos actuales.

## Rutas y autorización

GET /api/v1/financial/cash/associations/{associationId}/receipts/{receiptId}: JSON de snapshot. Requiere token, financial:cash:read y concesión read de CashAuthorizationProvider para la asociación.
GET /finanzas/caja/asociaciones/{associationId}/receipts/{receiptId}: JSON equivalente para sesión web.
GET /finanzas/caja/asociaciones/{associationId}/receipts/{receiptId}/imprimir: página Inertia Financial/CashReceipt, con botón Imprimir o guardar PDF.

Web mantiene auth, verified, session.active y device.track. Cada lectura vuelve a comprobar read para actor/associationId y filtra recibo por su movimiento/turno/caja. Un UUID ajeno a asociación autorizada devuelve 404; permiso insuficiente 403. No basta conocer el UUID, tener permiso operate/manage o abrir una impresión previa para recuperar acceso revocado. PendingCashAuthorizationProvider conserva su denegación.

API de recarga/retiro agrega folio y receipt_id; movimiento/manual e historial también. El historial carga la relación de comprobantes de forma anticipada para evitar una consulta extra por fila. No cambia el formato de éxito ni las claves de idempotencia.

## Interfaz e impresión

Caja y turnos muestra el folio en historial y agrega Ver e imprimir cuando hay comprobante. Abre una pestaña nueva; el servidor autoriza antes de entregar sus datos. La pantalla contiene los datos de operación y permite imprimir o guardar PDF con el diálogo del navegador; no requiere generador PDF en servidor. La impresión oculta botones y navegación, conserva datos y elimina el fondo de pantalla. Fechas presentadas en America/Mexico_City y moneda del snapshot. No se envía correo ni se publica un comprobante sin autenticación.

## Migración y pruebas

Nueva migración: 2026_10_09_200000_create_cash_receipts_table.php. Se mantienen las migraciones anteriores. Apply-Changes.ps1 verifica corte/hashes, ejecuta php -l y conserva respaldo. Restaura las variables de proceso.

Ocho pruebas nuevas: snapshot/folio conservados al reintentar tras cierre/renombrar; folios y transacciones de recarga/retiro sin duplicar dinero; rollback completo si falla comprobante de liquidación; rollback de movimiento manual; compatibilidad histórica sin documento inventado; API token/scope/asociación/UUID ajeno/lectura sin emisión; impresión web/sesión/permisos revocados; folio y receipt_id en respuestas e historial.

Los cuatro cleanup previos de caja eliminan comprobantes de sus fixtures antes de movimientos para respetar la FK. Esa limpieza está limitada a base financiera de pruebas y registros identificados por los prefijos ya existentes; no agrega borrado de datos operativos.

Revisión local: Vue compiló script/template de Cash y CashReceipt; imports App y enlaces/rutas contrastados; columnas, casts, relaciones, longitud de folio y hashes/ZIP revisados. PHP, SQL Server y MongoDB no están disponibles aquí: sintaxis y pruebas reales deben confirmarse con el verificador en el equipo del proyecto antes del commit.
