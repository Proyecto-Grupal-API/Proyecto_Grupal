# 2.5 Historial presupuestario protegido

Base b5d78b9. Agrega GET /finanzas/presupuestos-institucionales/{budgetId}/historial, nombre financial.institutional.history, y un enlace desde cada presupuesto consultable. No hay migraciones nuevas, permisos nuevos ni operaciones de escritura.

Reutiliza la sesión nativa registrada y vigente, cuenta elegible, correo verificado, segundo factor confirmado y las decisiones actuales budget.read.all O budget.read sobre el UUID concreto. Autoriza antes de buscar el presupuesto o consultar sus operaciones. No existe selector de actor/usuario ni filtro por negocio que reduzca indebidamente el historial del presupuesto. Se devuelve Cache-Control: no-store, private.

La pantalla muestra aprobación, ajustes, suspensión/reanudación, emisión, consumo, cancelación, vencimiento, devoluciones ordinarias, liquidaciones y devoluciones al presupuesto de BECA cerradas. Para cada operación expone fecha, motivo, UUID de operación, saldos registrados antes/después, versión y estado, junto con UUID relacionados admitidos.

Los snapshots se proyectan mediante una lista explícita. No se entregan before_data/after_data crudos, actor_id, beneficiarios, payer_reference, recipient_reference, referencias bancarias, idempotency_key, request_hash, datos de sesión o hashes nativos. El motivo es el texto de auditoría registrado por el operador y se presenta como texto escapado; no se interpreta como HTML. El historial no altera motivos históricos.

Los importes son cadenas decimales exactas, sin cálculos de coma flotante. Un snapshot inicial ausente se muestra como No registrado, nunca como cero. Campos mal formados quedan nulos y se marca recorded_fields_valid=false; acciones desconocidas se presentan como no reconocidas. Esto es una validación de formato para visualización, no una certificación contable. La conciliación continúa en la consulta de presupuesto existente.

El paginado usa ID descendente y cursor exclusivo before de hasta 18 dígitos, con 1..20 operaciones por página; action admite únicamente el catálogo conocido. Nuevas operaciones posteriores no desplazan la siguiente página de registros anteriores. Se puede reiniciar la consulta para ver lo más reciente. No se promete una fotografía transaccional de todo el historial a través de varias peticiones; la evidencia auditada es inmutable en el dominio.

Los servicios internos de lectura no sustituyen al control de acceso: el controlador verifica el permiso por presupuesto en cada solicitud. Fallos de autorización o de consulta producen una respuesta sanitizada; un presupuesto autorizado inexistente devuelve 404. La pantalla no concede permisos, no ejecuta conciliaciones ni abre endpoints de mutación.

Verify-Changes.ps1 ejecuta pruebas de lectura y seguridad, regresión institucional, las pruebas monetarias JavaScript y npm.cmd run build. Conserva .env y variables del proceso, desactiva E1/E4 reales y scheduler durante las pruebas y utiliza solamente SQL campus_digital_financial_testing y Mongo campus_virtual_testing. Prepara únicamente las migraciones de testing institucionales ya existentes. No modifica saldos de desarrollo.
