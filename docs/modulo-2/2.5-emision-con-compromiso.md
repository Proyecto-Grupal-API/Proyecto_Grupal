# Emisión BECA con compromiso presupuestario

Base revisada de Equipo 2: `b0e128c`. Segunda etapa del modelo de presupuesto institucional con pago posterior. Sin wallet financiadora, movimientos de efectivo ni liquidación al negocio.

## Alcance

InstitutionalBecaIssuanceService emite únicamente una BECA nueva y registra su compromiso presupuestario en la misma transacción SQL que el bono, su movimiento inicial, la auditoría administrativa y la operación presupuestaria. Si cualquier paso falla, se revierten todos. El servicio existente de administración conserva las validaciones de beneficiario, autoasignación, tipo de emisor, restricciones y permisos de emisión.

El servicio nuevo no tiene ruta web, API ni comando público. La administración por defecto sigue denegada. Requiere por separado:

- Facultad interna de E2 `budget.commit` sobre el presupuesto concreto. Es una acción del contrato interno, no un nuevo rol ni scope publicado por E1.
- Permiso web existente `bonus.issue`.
- Decisión positiva del proveedor específico para USER y BECA, consultada por el servicio administrativo. Los reintentos también revalidan esa decisión. E1 no otorga por ello facultad de comprometer cualquier presupuesto.

Un actor string no demuestra consentimiento ni sesión. El futuro controlador deberá tomarlo de sesión confiable y aplicar el guard administrativo existente. No exponer este servicio directamente a payloads de servicio sin evidencia del actor. No se instalan concesiones ni usuarios, ni se recupera la propuesta de siete plazas.

## Entrada y reglas

El servicio recibe actor, UUID de presupuesto, versión esperada, datos de emisión e idempotency key. Los datos incluyen `award_reference`: referencia estable del otorgamiento, distinta de la clave de reintento. Debe estar prefijada por su origen y usar representación canónica, por ejemplo `institucion:programa:otorgamiento`. No se define con ello un contrato de E6 ni se certifica la legitimidad del dictamen.

El UUID y clave se normalizan a minúsculas; la referencia de otorgamiento se conserva sin espacios exteriores y se compara conforme a la collation de SQL Server. La referencia es única en la tabla de compromisos: una nueva clave no puede duplicar el mismo otorgamiento. El consumidor debe conservar esa referencia en todos los reintentos.

El presupuesto debe estar activo, vigente y ser BECA en MXN. No hay conversión de monedas. El importe debe ser un entero positivo real en centavos y no superar aprobado menos comprometido menos consumido. La vigencia completa del bono debe estar dentro de la del presupuesto. Se exige la versión revisada para rechazar una solicitud preparada antes de otro cambio; quien recibe conflicto debe consultar de nuevo y revisar, no inventar una versión.

La fila de presupuesto se bloquea al comprobar capacidad y se incrementa su versión al comprometer. El índice único del otorgamiento y los índices de bono/operación protegen la relación. El compromiso conserva presupuesto, bono, operación, referencia de otorgamiento, importe y moneda. Los compromisos de esta entrega son evidencia inmutable de emisión, no un ledger de liquidaciones.

Los replays devuelven la operación histórica sin reservar ni emitir nuevamente, después de revalidar permisos e integridad básica del vínculo. Si presupuesto u operación cambiaron después, el snapshot original no representa su estado actual. Se rechaza reutilizar la clave con otro contenido, actor, presupuesto o versión.

El actor del presupuesto y del bono es el mismo sujeto en este flujo inicial. Permiso para aprobar presupuesto no supone permiso para emitir, ni viceversa. Las referencias de institución/pagador deben acreditarse antes de habilitar uso real.

## Compatibilidad y cierre del ciclo de vida

No se permite vincular una emisión administrativa anterior ni adjuntar presupuesto a bonos históricos. Solo el bono creado dentro de esta transacción recibe institutional_budget_id. El marcador no se expone como campo editable del formulario y se protege contra cambios posteriores en el modelo. Su asignación inicial usa el writer SQL privado de este flujo; el acceso directo a DB queda fuera de la frontera de seguridad de la aplicación.

Los bonos anteriores, sin marcador, conservan el comportamiento vigente. En cambio, consume, consumeMultiple, cancel, expireIfNeeded y addRestriction rechazan un bono vinculado. Aún falta el ciclo presupuestario de consumo/liberación/reembolso; se bloquea la ruta heredada para que no deje el compromiso desactualizado. En combinaciones se detectan bonos vinculados antes de expirar los demás.

Un bono vinculado vencido todavía conserva su saldo registrado mientras este cierre está activo. La consulta de exposición lo clasifica sin modificarlo. No ejecutar reparaciones o cancelaciones manuales para liberar presupuesto. Las compras con estos bonos permanecen inhabilitadas hasta completar el ciclo, sus obligaciones de pago y las autorizaciones.

No se cambia el comportamiento general de emisión histórica/no vinculada del dominio. Esto no habilita esa vía para producción: el autorizador web pendiente sigue bloqueándola. La futura interfaz BECA debe llamar al servicio presupuestario, no abrir el endpoint genérico como alternativa sin presupuesto.

El diagnóstico de exposición cambia su indicador funding_evidence a NOT_CHECKED_BY_THIS_REPORT: ya existe metadata de vínculo, pero ese reporte no la inspecciona y no certifica financiamiento ni efectivo. funding_certified sigue siendo false. Es un cambio del JSON operativo CLI; no se modifica una API pública.

## Límites y validación

Se conservan los modelos/consultas locales de identidad ya presentes en el administrador. No se declara completada la independencia de E1. No hay transacción distribuida con Identidad: una revocación externa posterior a la decisión requiere coordinación del contrato, y las consultas del proveedor durante emisión pueden prolongar el bloqueo SQL. No se cachean permisos positivos para evitar estas consultas.

Las pruebas incluyen emisión con compromiso real, replay, cambio de datos, capacidad y versión, vigencia/moneda, permisos separados, proveedor indisponible, rechazo de vinculación histórica, rollback de auditoría y compromiso, integridad del replay y bloqueo de ciclo heredado. Las pruebas de versiones/locks no equivalen a una prueba multiproceso certificada.

La migración añade institutional_budget_id nullable a bonuses y una tabla de compromisos; no marca bonos existentes ni mueve saldos. Se requiere la migración presupuestaria base antes de la nueva. El verificador prepara ambas en SQL Server de testing después del preflight exacto. Sin -MigrateDevelopment no cambia el esquema de desarrollo. Antes de usar el flujo en desarrollo habrá que aplicar ambas, una vez aprobadas las pruebas.

No se ejecutaron PHP, Pest ni SQL Server en la preparación. Verificar en Windows antes del commit. Las pruebas usan un proveedor permisivo solo dentro del proceso aislado y revierten los registros SQL; no habilitan permisos en el producto.
