# 2.6 - Destinatarios, confirmación e interfaz

Base: 1d3b82b. Complementa el bloque 2.6-base-transferencias. No concede permisos ni modifica roles, .env ni módulo 1.

## Flujo

Finanzas > Transferencias y regalos. Preparar identifica al destinatario y muestra nombre, matrícula si existe, identificador de cuenta, monto, tipo y concepto. Preparar no reserva ni mueve dinero. Cada preparación fija los datos en servidor, vence y solo puede confirmarla o cancelarla su emisor. Confirmar exige confirmed=true y un encabezado Idempotency-Key; rechaza otros campos. Cambiar datos requiere otra preparación.

La política conserva los montos previos ($1 mínimo, $2000 máximo, $5000 diario, $20000 mensual) y agrega confirmation_seconds=300. Es un plazo inicial de desarrollo configurable con permiso canManagePolicy, versión esperada y motivo. La migración incrementa y audita la versión al agregarlo. Modificar el plazo solo afecta nuevas preparaciones; los importes y habilitaciones vigentes se reevalúan al ejecutar cualquier preparación pendiente. Una ejecución conserva el snapshot de la política realmente aplicada.

No existen valores económicos vacíos. Valores en centavos enteros positivos; plazo entero positivo. El techo de 2147483647 segundos es técnico y no una recomendación de duración. Calendario contable conservado America/Mexico_City.

## Integración con identidad

TransferRecipientProvider::resolve(method, value, actorId, ip) retorna solo user_id, name y enrollment_number. Module1TransferRecipientAdapter es el adaptador temporal hacia los modelos disponibles y el contrato IdentityProvider. Después puede sustituirse por el contrato oficial del Equipo 1 sin cambiar la pantalla ni el servicio de confirmación.

USER_ID exige el ID real de cuenta de 24 caracteres (no se implementa búsqueda por nombre o email). ENROLLMENT consulta la matrícula exacta y rechaza duplicados; el perfil tiene que resolver un ID de cuenta válido. No se considera el ID del perfil como dueño de wallet. Las cuentas se validan activas/verificadas y la wallet personal MXN debe ser única.

QR usa exclusivamente IdentityProvider::validateQr con actor, IP y contexto FINANCIAL_TRANSFER_RECIPIENT. Se acepta identity.user_id o identity.id, ambos ID de cuenta válido; una respuesta malformada o servicio caído devuelve 503, un QR rechazado devuelve 409. No se adivina identidad ni se leen tokens por fuera del contrato.

LIMITACIÓN CONOCIDA: en el corte revisado IdentityService llama User::displayIdentity(), pero User no define ese método. Este paquete no modifica código del Equipo 1: la opción QR puede responder 503 hasta que se corrija esa integración o se sustituya el adaptador. Las pruebas QR comprueban la integración con un contrato simulado; NO certifican que el servicio QR real funcione. ID y matrícula se conectan al código disponible.

No se guarda el QR crudo en SQL, solo un hash de la solicitud. El servicio de identidad registra su propia validación y puede consumir el QR dinámico al resolverlo. Si identidad confirma el QR y luego SQL falla, no existe una transacción distribuida entre Mongo/SQL para desconsumirlo: podría necesitarse un nuevo QR y otra preparación. Un replay de una preparación ya guardada no vuelve a validar/consumir el QR.

## API de la interfaz

Todos los endpoints utilizan sesión Fortify y middleware auth, verified, session.active, device.track, financial.correlation y CSRF de web. Preparación y confirmación tienen throttle 30 por minuto. Axios consume estas rutas JSON desde Vue; no se almacenan tokens de servicio en navegador.

| Verbo | Ruta relativa a /finanzas/transferencias | Uso |
| --- | --- | --- |
| GET | / | Página Inertia, wallet propia, política, permisos |
| GET | /records | Historial propio enviado/recibido paginado (20) |
| GET | /{transferId} | Operación, solo participantes |
| GET | /confirmations | Preparaciones propias pendientes paginadas (incluye vencidas para cancelarlas) |
| POST | /confirmations | Identificar y preparar, Idempotency-Key |
| GET | /confirmations/{confirmationId} | Datos inmutables, solo emisor |
| POST | /confirmations/{confirmationId}/confirm | Confirmar/reintentar, Idempotency-Key |
| POST | /confirmations/{confirmationId}/cancel | Cancelar preparación; idempotente |
| PATCH | /policy | Cambiar límites/plazo/habilitación con versión y motivo |
| GET | /policy/history | Historial administrativo paginado |

No se agregan en este bloque rutas OAuth de terceros en /api/v1: un token de servicio no identifica automáticamente al estudiante ni puede escoger un sender_id. Para esa integración falta una delegación confiable definida en el contrato; nunca se debe sustituir por un campo del body. El requisito de Docker sigue pendiente del bloque de despliegue; este paquete no modifica contenedores.

## Permisos y privacidad

TransferAuthorizationProvider controla envío, recepción y administración. Su adaptador pendiente sigue denegando por defecto. Los roles autoasignados no habilitan acciones. El dueño puede consultar sus preparaciones e historial incluso si después pierde permiso de enviar; confirmar siempre revisa permisos nuevamente. Historial de envío/recepción está aislado por participantes. No se expone saldo del destinatario, email, claves QR ni perfiles completos.

Los datos de origen y el actor salen de la sesión, aunque un cliente mande sender_id o una IP falsos. La confirmación registra requested_ip, confirmed_ip, correlación y fecha desde el servidor. El emisor puede recuperar su preparation y el execution_key de retry después de recargar la página; esa clave no es autorización por sí sola y nunca se muestra a otros usuarios. Se permite cancelar una preparación propia tras perder permiso; un envío completado se gestiona mediante el reverso autorizado del 2.7, no esta cancelación.

## Atomicidad y recuperación

Un mutex SQL con fencing serializa la preparación por request_key y la confirmación por su clave de ejecución. La primera confirmación fija execution_key en una transacción breve independiente: si falla dinero, ese intento conserva su identidad para retry. No puede reutilizarse la misma execution_key en otra preparación. Las claves se normalizan como en la base.

StudentTransferService añade un callback interno onCompleted opcional, sin cambiar el comportamiento de las llamadas existentes. La confirmación usa el callback dentro de la transacción contable para comprobar otra vez vigencia, estado e identidad ligada de wallets/destinatario, y guardar COMPLETADA + referencia al envío. Un fallo de esa escritura revierte ambas wallets, ledger y StudentTransfer. La tabla de confirmaciones no se guarda en una transacción externa que pudiera borrar la evidencia de límites 2.10: los bloqueos 2.10 siguen persistiendo después del rollback financiero.

Cancelar concurrentemente una preparación hace que el callback rechace y revierta el dinero; si ya se guardó COMPLETADA, cancelar la rechaza. No se afirma que las pruebas de fallas simuladas ejecuten dos procesos SQL concurrentes reales. No se reserva el saldo al preparar: puede cambiar antes de confirmar y entonces se rechaza sin movimiento parcial.

La pantalla conserva payload y claves en cada intento, muestra errores y no cambia la clave al reintentar. Preparaciones pendientes permiten recuperar los datos y el retry del servidor tras una recarga. Un error actualizando listados luego de una ejecución no convierte el envío en fallido. La política utiliza bloqueo por versión para evitar sobrescrituras de cambios administrativos.

El historial presenta kind TRANSFERENCIA/REGALO y el estado actual de FinancialTransaction; conserva executed_status de la ejecución original. Los regalos mantienen el par contable TRANSFERENCIA_SALIDA/TRANSFERENCIA_ENTRADA y referencia STUDENT_GIFT para compatibilidad con conciliación y reversos.
