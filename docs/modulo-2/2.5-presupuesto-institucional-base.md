# Presupuesto institucional BECA primera etapa

Base: Módulo 2 `491f6d8`. Modelo funcional elegido: presupuesto institucional aprobado y pago posterior. No se requiere wallet financiadora ni se declara que el presupuesto equivale a efectivo custodiado.

## Alcance implementado

- Esquema SQL Server para presupuestos e historial de operaciones.
- Servicio administrativo para aprobar, ajustar el importe total, suspender y reactivar.
- Referencias explícitas de institución, aprobación y responsable del pago. Son referencias documentales, no prueba automática de la legitimidad de la aprobación.
- Presupuesto limitado a BECA; una moneda por registro e identidad de aprobación única por institución.
- Importes enteros positivos en centavos y restricciones SQL que impiden comprometido/consumido negativos o superiores al aprobado. El máximo representable es el entero PHP/SQL Server, no un tope institucional aprobado.
- Clave de idempotencia para cada operación, huella de actor/acción/datos, bloqueo por solicitud, bloqueo SQL del presupuesto y versión esperada para actualizaciones.
- Actualización e historial en una misma transacción. Un fallo al guardar auditoría revierte la operación. Los reintentos verifican nuevamente autoridad antes de recuperar una respuesta anterior.

`available_amount_cents = approved_amount_cents - committed_amount_cents - consumed_amount_cents` representa capacidad contable restante, no autorización para usar un presupuesto suspendido, vencido o sin autoridad. No significa dinero depositado. Los presupuestos nuevos comienzan con comprometido=0 y consumido=0.

## Administración cerrada

InstitutionalBudgetAuthorization es un límite interno de E2. Sus acciones budget.approve, budget.adjust, budget.suspend y budget.resume NO son capacidades nuevas publicadas por E1 ni roles acordados. El proveedor por defecto deniega todas las acciones. No hay bandera para permitirlas automáticamente, interfaz web, API o comando de escritura.

El actor debe ser el ID canónico de Identidad y debe proceder de evidencia confiable del futuro controlador/adaptador. Un string actor no demuestra sesión, consentimiento ni segundo factor. El proveedor aprobado deberá verificar cuenta, autoridad y ámbito; este paquete no los inventa. Las referencias de institución y pagador deben acreditarse mediante el procedimiento institucional antes de habilitar aprobación real.

El servicio se resuelve en el contenedor con el proveedor que deniega todo. Los proveedores permisivos de las pruebas solo existen dentro de los fixtures. No se insertan cuentas, roles, presupuestos o permisos al instalar o migrar. La migración solo crea estructura vacía.

## Idempotencia y concurrencia

Las claves se normalizan a minúsculas, con el mismo criterio que las claves financieras anteriores. Una clave repetida con el mismo contenido devuelve la operación histórica y su snapshot original, incluso si el presupuesto cambió posteriormente. La misma clave con otro contenido, actor o acción produce conflicto. El replay no representa el estado actual del presupuesto.

La referencia de aprobación es única por institución, incluso si llega otra clave. Cambiar el importe exige otro movimiento sobre el presupuesto existente, no un segundo presupuesto con la misma aprobación. Cada ajuste o cambio de estado exige la versión vigente y bloquea la fila SQL. Una petición con versión antigua no puede sobrescribir otra modificación. Se rechazan ajustes sin cambio y la reactivación de un presupuesto vencido.

Las pruebas verifican versiones antiguas y un lock de solicitud ocupado. No se declara probada concurrencia multiproceso ni recuperación de todas las condiciones distribuidas. La aprobación externa y las comprobaciones de identidad no forman parte de una transacción distribuida con SQL Server.

## Lo que aún no está implementado

Este primer paquete NO reserva presupuesto por bono, no actualiza los contadores al consumir y no crea obligaciones de pago. Esos contadores están preparados y protegidos por restricciones SQL, pero no hay un writer de ciclo de vida expuesto. No se debe integrar emisión real llamando a approve y luego a BonusService por separado.

La siguiente etapa vinculará presupuesto, compromiso por bono y emisión dentro de la misma transacción SQL; después consumo y obligación por compra, liberación de saldo no utilizado, reembolsos y liquidación posterior. No se debe confundir consumed_amount_cents con deuda ya pagada. Las compras existentes no cambian con este paquete.

Los bonos históricos no se asignan a presupuestos nuevos automáticamente. Se mantiene el diagnóstico de exposición existente y el indicador de respaldo no registrado. No modificar ese indicador para afirmar respaldo de bonos que aún no tienen vínculo.

Siguen pendientes autoridad institucional de aprobación presupuestaria, autoridad de emisión de E1, límites por periodo/beneficiario, evidencia del responsable de pago y política final de recuperación/reembolso. No se recupera la propuesta de siete plazas rechazada.

## Validación y operación

Ejecutar el verificador antes del commit. Solo utiliza Mongo campus_virtual_testing y SQL Server campus_digital_financial_testing; los nombres se comprueban antes de cargar TestCase y de migrar pruebas. TestCase elimina la base Mongo de pruebas al iniciar cada caso. No se deben suprimir estas guardas ni apuntar la suite a bases de desarrollo/integración.

La migración es aditiva y solo crea dos tablas nuevas. -MigrateDevelopment es opcional y prepara el esquema en desarrollo; no registra aprobaciones ni habilita acciones. El verificador prepara siempre la migración en SQL Server de testing. No aplica migraciones generales ni ejecuta seeders. El rollback se niega a borrar las tablas si hay presupuestos o historial.

Se incluyen pruebas para proveedor cerrado, aprobación, auditoría sin dinero ni bonos, replay, cambio de contenido/actor, referencia duplicada, ajuste con versión, capacidad comprometida y consumida, suspensión, revocación de permiso, rollback de auditoría, entrada inválida, lock ocupado y vigencia. La prueba de capacidad usa contadores explícitos de fixture, no anuncia un flujo real de reserva.

No se ejecutaron PHP, Pest ni SQL Server durante la preparación del paquete. Las comprobaciones estáticas y de integridad no sustituyen la salida de Verify-Changes.ps1 en el equipo del usuario. No hay cambios Vue ni necesidad de npm build.
