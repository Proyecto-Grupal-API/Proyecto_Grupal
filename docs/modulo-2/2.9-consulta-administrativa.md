# 2.9 — Consulta administrativa independiente

Base: commit07f2013. La consulta personal y la API delegada permanecen intactas. Se agrega una función web de consulta puntual de comprobantes ajenos; no un listado global ni una emisión nueva.

## Uso

Finanzas → Mis comprobantes → Consulta administrativa. Elegir transacción o pago de compra, introducir UUID de operación y UUID de la wallet cuya participación se consulta. Para pagos con negocio, seleccionar business y el ID real registrado. Para operaciones vinculadas a caja, association y su ID real. Para operaciones sin contexto registrado, dejar contexto vacío. Un UUID de bono no es un UUID de pago.

GET /finanzas/comprobantes-administracion muestra únicamente el formulario, sin datos administrativos. GET /finanzas/comprobantes-administracion/lookup exige sesión verificada, segundo factor confirmado y autorización administrativa; devuelve data. Frecuencia30/minuto del middleware Laravel. No existe endpoint administrativo con token de servicio en esta entrega; la API personal del2.9 sigue requiriendo delegación.

La interfaz no imprime un comprobante administrativo nuevo, cambia saldos, crea wallet, ni cambia snapshots. El resultado filtra la participación de la wallet seleccionada: no muestra ledger de otras wallets ni metadatos, razones, actores de caja o supervisor. No se agregó bitácora de lectura; la bitácora existente de autorización registra cambios de permisos, no estas consultas. Una bitácora de acceso persistente requiere su propia política de retención y será una función separada.

## Autorización y separación

ReceiptAdministrativeAuthorization::assertRead(userId, scope) es el puerto independiente. El actor se deriva exclusivamente de la sesión. actor_id/user_id/principal enviados se rechazan. El proveedor se consulta antes de buscar la operación y nuevamente con su contexto derivado. null significa operación sin contexto, nunca comodín.

Pendiente por defecto: PendingReceiptAdministrativeAuthorization falla con503. Adaptador optativo CampusReceiptAdministrativeAuthorization consulta Kernel::principalFor y check(module.2.9.read, scope). No hay fallback que amplíe permisos. Las siete plazas globales conservan la lógica del núcleo; los permisos modulares requieren la capacidad de lectura concreta. create/approve/execute/cancel/configure no sustituyen read. La revocación, inactividad y fecha inicial/final son evaluadas en cada consulta por el núcleo, sin caché positiva.

El contexto se deriva así:
- Compra: purchase_payments.business_id; nunca metadata o ID aportado como prueba de pertenencia.
- Transacción PURCHASE: pago asociado a su idempotency_key y a la wallet seleccionada; requiere enlace existente.
- Caja: CashMovement vinculado por wallet/idempotency/reference_type/reference_id y asociación del registro de caja.
- Operación con original_transaction_id: hereda el contexto de la original, con máximo5 enlaces; incoherencia o enlace inaccesible se bloquea.
- Otros movimientos: sin contexto. Una recarga/retiro EFECTIVO sin enlace de caja no se degrada a sin contexto:409.

Si el contexto solicitado no coincide con el registrado,404. Contexto sin registro autorizado en campus_authorization_contexts:403 incluso para plaza global, por el comportamiento del núcleo. No se insertan asociaciones/negocios ficticios para sortearlo. El registro de contextos debe provenir de entidades y fuentes verificadas del proyecto. Los ámbitos service/council no se ofrecen porque todavía no hay vínculo fiable de estos tipos a las operaciones consultadas.

## Activación explícita y reversibilidad

No se modifica .env al instalar. Para usar el núcleo propuesto, establecer en .env:

```
FINANCIAL_RECEIPT_ADMIN_PROVIDER=campus
CAMPUS_AUTHORIZATION_ENABLED=true
```

Ejecutar php artisan config:clear y reiniciar procesos de desarrollo. Se necesitan plaza global o permiso modular module.2.9.read, cuenta activa, correo verificado y segundo factor confirmado. El estado anterior de roles embebidos no da permisos.

Para desacoplar el núcleo sin retirar interfaz:

```
FINANCIAL_RECEIPT_ADMIN_PROVIDER=pending
```

config:clear. Las consultas administrativas se bloquean con503, y las personales siguen funcionando. No elimina roles, comprobantes ni historial. Valores de proveedor no reconocidos también bloquean con503. Para conectar el contrato oficial se implementa el puerto y se registra su proveedor explícitamente; no se modifica el servicio financiero.

## Validación

Ocho pruebas nuevas usan el núcleo real con Store/Directory de pruebas: sesión/2FA, plaza global y aislamiento de participación, contexto de negocio, revocación y acción independiente, contexto inválido/inactividad/actor falso, proveedor pendiente/desactivado/erróneo, vigencia futura y contexto de caja. Las pruebas anteriores del núcleo ya cubren concurrencia MongoDB; no se introduce escritura de autoridad en esta función. Los componentes Vue pasaron parse/compile locales; PHP/SQL Server/MongoDB no están disponibles en el entorno de preparación. Ejecutar Verify antes de commit.
